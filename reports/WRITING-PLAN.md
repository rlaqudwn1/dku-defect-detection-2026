# 기술보고서 작성·자동화 계획

2026-11-18 보고서 준비 시작: [현재 연구 계획](../docs/research/RESEARCH-PLAN-2026-11-18.md), [원고v0.1](drafts/REPORT-v0.1.md), [주장 장부](context/claims.json), [출처 역할](context/SOURCES.md), [BibTeX](references.bib)를 사용한다. 아래 초기 Q1–Q4와 앙상블 계획은 당시 제안이며 현재의 의무 실험 목록이 아니다. 최종 제출 형식·마감·채점 공지의 현재 유효성은 별도 확인한다.

현재는 과제·질문·자료 기술·관측 범위·기준선 구현·한계를 쓴다. 대회 성능과 최종 결론은 미측정으로 남긴다. 이미지당 출력은 보정이 확인되지 않은 **불량 점수**이며 확률이라는 표현을 자동으로 쓰지 않는다.

수업 프로젝트 평가는 기존 공지 기준 기술보고서가 65%다. 보고서는 점수만 나열하지 않고 모델 선택·대안·실험·실패·해석·재현을 설명한다. 별도 분량 제한은 없으며 제출 파일 형식은 후속 공지를 확인한다.

## 연구 질문을 먼저 정하기

초기 질문 제안은 다음과 같다. 이는 확정된 결과나 교수의 요구 문장이 아니다.

- Q1: 전체 이미지를 사용하는 작은 기준 모델이 어떤 검증 성능과 실행 비용을 보이는가?
- Q2: 입력 크기·비율 보존이 작은 결함 분류와 실행 비용에 어떤 영향을 주는가?
- Q3: 데이터 불균형을 고려한 학습 변경이 AUROC를 개선하는가?
- Q4: 서로 다른 오류를 내는 두 모델의 확률 앙상블이 단일 모델보다 나은가?

각 질문은 연구 카드 → 실험 계획 → run → 결과·실패 분석 → 보고서 문장으로 연결한다. 논문이나 공개 코드에 있는 주장과 우리 데이터에서 확인한 결과를 구분한다.

## 절별 작성 근거

| 절 | 답할 질문 | 사용할 증거 |
|---|---|---|
| Abstract | 무엇을 했고 무엇을 확인했는가? | 최종 선택과 확인된 주요 결과; 마지막에 작성 |
| Introduction | 과제와 목표가 무엇인가? | 이미지당 불량 점수, 대회 지표·제약 |
| Related Work | 왜 이 접근을 후보로 골랐는가? | 직접 읽은 원문·공식 코드, 장단점과 적용 한계 |
| Methods | 다른 사람이 무엇을 그대로 실행해야 하는가? | 모델·전처리·split·손실·최적화·seed·ensemble recipe |
| Experiments & Results | 어떤 비교를 어떻게 했는가? | 같은 split의 단일/튜닝/앙상블 결과와 실행 환경 |
| Discussion | 왜 개선·악화됐고 무엇을 모르는가? | 실패 실험·오류 사례·검증 편향·시간 제약 |
| Conclusion | 근거가 지지하는 결론과 다음 실험은? | 실제 결과 범위 내 결론; 과장하지 않음 |
| References | 어떤 자료를 사용했는가? | 논문·코드·모델·가중치 출처와 라이선스 확인 기록 |
| 재현 부록 | 선택 모델과 제출물을 어떻게 다시 만드는가? | 고정 버전·커밋·환경·실행 명령·검사 결과 |

## 자동 생성할 표·그림

1. 데이터 분할·클래스 수·중복 검사 요약.
2. 실험 비교표: ID, 변경 변수, split 해시, AUROC, epoch/총 시간, peak VRAM, 상태.
3. 선택 모델의 학습/검증 loss와 AUROC 곡선. 시간축과 epoch축을 구분한다.
4. 단일 모델과 앙상블 비교표: 구성원 버전·가중치·검증 AUROC·추론 비용.
5. 재현 검사표: 파일 해시, 예측 차이, AUROC 차이, 형식 검사, 실행 환경.

결과 파일에서 CSV·Markdown 표와 정적 그림을 생성하도록 한다. 수치를 원고에 따로 수동 복사하는 곳을 줄인다. 완료 실험의 성능 비교표와 OOM/실패·중단 목록을 분리하되 실패 목록도 보고서에 남긴다. 서로 다른 split이나 평가 프로토콜은 별도 비교군으로 표시한다. 성능 향상의 유의성을 확인하지 않았다면 근소한 차이를 확정적 우월성으로 표현하지 않는다.

W&B Reports는 run 비교 그래프와 연구 분석을 모으는 작업 문서로 사용한다. 제출 원고의 본문·참고문헌과 재현 부록은 Git에서 관리하고, 제출 시점에는 run 집합·Artifact 버전·표를 고정한 스냅샷을 남긴다. 최종 형식이 확정되면 PDF/LaTeX/요구 형식으로 내보내는 경로를 점검한다.

## 작성 시점

- baseline 전: Introduction 초안, 데이터·환경·분할 설명, Related Work 후보 카드.
- 각 실험 직후: 변경 이유, 결과, 실패·해석, 다음 실험을 카드에 기록.
- 최종 선택 전: Methods·결과표·한계 초안을 완성하고 누락된 비교를 확인.
- 제출 리허설 후: 재현 부록과 실제 검사 결과를 반영.
- 결과 확정 후: Abstract·Conclusion 작성, 본문 수치·표·출처 대조.

실험 결과가 없으므로 현재 보고서에 성능 수치를 채우지 않는다. 생성형 문장 작성 여부와 무관하게 실제 실험·원문·구현으로 설명할 수 있는 내용만 사용한다.

## 주장과 표본의 추적

핵심 주장마다 가설 ID, 비교 run 집합, 데이터/split/평가 프로토콜, 표·그림 생성 입력, 관측, 해석, 반례·한계를 한 행으로 연결한다. EDA 그림·오류 사례는 표본 선택 기준과 ID를 보존한다. 설명용 시각화만으로 원인을 입증했다고 쓰지 않는다. threshold 기반 오류를 보이면 threshold 선택 근거를 남긴다.

OOM·중단·데이터 오류 같은 시스템 실패와, 정상 완료했지만 가설이 지지되지 않은 결과를 구분한다. 둘 다 비용과 보고서 근거에 남긴다. 보고서 도메인 자문과 페어리뷰는 근거와 주장의 일치 여부를 검토하며 실제 실험 성공을 대신 선언하지 않는다.

## 작성 문맥의 관리

절별 brief·claim 장부·필요 근거·검토/처분·변경 영향·제출 스냅샷은 [보고서 문맥 관리 하네스](../docs/REPORT-CONTEXT-HARNESS.md)를 따른다. 현재 CLI는 결과표·문맥 묶음·변경 확인·고정 근거 묶음을 지원한다. 본문 생성·자동 인용·주장의 과학적 타당성을 자동 보장하지 않는다. 이번 초안과 주장 장부는 별도 작성한 준비물이다.
