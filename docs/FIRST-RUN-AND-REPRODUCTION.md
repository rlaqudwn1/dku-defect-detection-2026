# 첫 실행·재현 묶음의 필수 계약

2026-11-17 운영 기준: [운영 진입점](OPERATIONS.md) → [현재 상태](CURRENT-STATUS.md)에서 시작한다. 아래 본문은 구현 전 설계 의도·완료 조건의 이력이며 당시 상태나 제안 명령은 현재 실행 지시가 아니다. 실제 CLI는 [실행 가이드](RUNBOOK.md)와 소스·테스트를 따른다.

현재: ResNet18 시작 설정·CPU 환경·합성 기능/재개 검사는 있다. 실제 대회 P000·성능·Colab GPU·새 환경 재현은 없다. 아래는 첫 실제 대회 실행과 최종 재현 전에 채울 설계 체크리스트다.

## 1. 첫 baseline과 P000 전에 채울 항목

| 범위 | 반드시 결정·기록할 것 | 확인 방법 |
|---|---|---|
| 모델·가중치 | 코드·정확한 가중치 출처/버전/hash·공개일 근거·사용 조건·권장 입력 변환 | 첫 학습과 임베딩 encoder 모두 동일 확인; 공개 기준은 2026-11-15까지 |
| 디코더 | 색상 변환·EXIF 방향·손상 처리·배치 경로 | 전수 디코드 결과와 작은 고정 이미지 집합 |
| 입력 전처리 | resize/pad·보간·정규화·train/eval 변환·크롭 여부·변환 fitting 범위 | 원본/변환 비교와 별도 validate/predict 입력의 일치 |
| 출력·loss | head 출력의 의미·양성 클래스·loss·logit→불량 확률 변환 위치·정밀도 | 양성은 1; 이중 sigmoid 등 방지; 완벽/역전 예측으로 지표 방향 확인 |
| 최적화 | optimizer·weight decay·학습률·scheduler·갱신 단위·warmup·freeze 정책 | resolved config와 실제 optimizer step 수 |
| 학습 기회 | batch·accumulation·유효 batch·epoch/step 예산·증강·sampler/loss 재가중 여부 | 후보 변경 시 새 설정/run; 보정을 겹치면 별도 근거 |
| 정밀도 | AMP 사용 여부·dtype·지원 실패 시 정책·지표 계산 정밀도 | 비유한 loss/gradient/확률 검사; 조용한 설정 변경 금지 |
| 선택 | best 지표·평가 시점·early stopping·동점 규칙 | 실행 전 기록; 실제 선택 epoch와 근거 |
| 재개 | model·optimizer·scheduler/scaler(사용 시)·epoch/step·난수/데이터 순서·run ID | epoch 경계 저장·재개 비교 |

예를 들어 1-logit head와 BCEWithLogitsLoss를 사용한다면 평가에서 sigmoid를 한 번 적용하는 경로를 명시한다. v0.1 시작 경로는 이 구성을 사용하지만 대회용 최종 아키텍처 선택은 아니다. 여러 제품·view·patch를 사용하면 부모 이미지로 집계한 뒤 이미지당 확률 하나를 낸다.

## 2. 짧은 기능·재개 검사

- 작은 합성 데이터로 학습→검증→테스트 예측→가중치 재로딩 경로를 검사한다.
- 제공 학습 부분의 작은 표본에서 유한한 loss/gradient/확률과 학습 반응을 확인한다. 표본 과적합 점수는 일반화 성능이 아니다.
- 같은 고정 이미지가 학습 중 평가 경로와 별도 validate/predict에서 같은 평가 입력·점수를 내는지 확인한다.
- 배치 순서가 바뀌어도 ID별 점수가 같고, 여러 view는 부모별 집계 후 행 수가 맞아야 한다.
- 중단 없는 짧은 실행과 epoch 경계 재개 실행의 step·scheduler·상태·예측 차이를 비교한다.
- 단지 checkpoint를 읽었다는 사실과 중단 없는 학습의 수치 동등성은 별개로 기록한다.

실제 학습 검사는 지금 수행하지 않았다.

## 3. 최종 재현 묶음의 최소 내용

1. 코드 commit과 dirty 변경 처리 정책. 사용한 변경은 패치/hash로 보존하거나 깨끗한 선택 버전으로 고정한다.
2. resolved config·전처리·양성 방향·split·데이터 manifest와 hash.
3. Python·검증된 패키지 설치 목록 또는 잠근 환경, OS·GPU·CUDA/cuDNN·precision·결정론 설정.
4. 선택한 checkpoint의 정확한 버전/hash와 로컬 전달 파일. ensemble이면 모든 구성원과 집계 recipe.
5. 상대 경로 인자와 학습/검증/추론을 나눈 실행 방법. 개인 Drive 절대 경로를 코드에 고정하지 않는다.
6. 원래의 검증 예측·AUROC·테스트 예측/제출 CSV hash와 비교 방법.
7. 새 세션에서의 설치·가중치 로드·검증·추론·재개 검사 중 실제 수행한 항목과 결과·한계.
8. 개인 W&B/GitHub/Drive 인증 없이 평가자에게 필요한 파일을 전달할 경로. 구체 전달 방법은 후속 제출 안내를 확인한 뒤 최종 묶음 확정 전에 결정한다.

최종 추론은 제출된 가중치를 읽어야 하며 초기화용 pretrained 파일을 불필요하게 다시 다운로드하지 않도록 설계한다. W&B 연결 없이도 제출 코드와 제공 파일로 검증·추론할 수 있는 경로를 포함한다.

## 4. 통과와 남는 한계

파일 hash는 정확한 바이트 무결성, 행별 확률·AUROC 차이는 수치 재현성으로 구분한다. 허용오차 측정 방법은 P000에서 정리하고 최종 예정 추론 경로의 같은 가중치 반복 평가로 확인한다. 최종 선택 전에 기준을 고정하며 실패 뒤 임의로 완화하지 않는다. 수치 허용오차 통과가 CSV 바이트 hash 동일을 자동 의미하지 않는다.

빈 새 환경에서 문서와 전달 파일만으로 검증 AUROC·800행 예측·선택 ensemble을 재생성해야 한다. 학습 재실행·중단 복구·고정 가중치 재현의 수행 여부는 각각 기록한다. 다른 GPU/버전의 비트 단위 동일성을 약속하지 않는다.

이 문서에 항목이 있다는 사실은 설정 확정·환경 제공·실제 재현 성공 증거가 아니다. 모델 선정 후 실제 값을 채우고 구현·검사해야 한다.
