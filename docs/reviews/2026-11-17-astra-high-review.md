## 종합 판정

**가벼운 연구 저장소의 출발점으로는 적절하지만, 아직 첫 본학습이나 튜닝에 들어갈 준비가 끝난 것은 아니다. 가장 큰 공백은 도구의 수가 아니라, 연구 질문에서 데이터 조사·검증 설계·실험 선택으로 이어지는 결정 절차다.**

가설 필드는 이미 있고, EDA도 한 문단으로 언급되어 있다. 따라서 “가설과 EDA가 전혀 없다”는 평가는 부정확하다. 문제는 실제 첫 작업이 `P000 → E001 모델 → E002 학습률`로 제시되고, 그 전에 어떤 관측으로 어떤 가설·분할·전처리를 채택하거나 버릴지 정하는 산출물과 통과 조건이 없다는 점이다. 현재의 더 큰 위험은 실험을 기록하지 못하는 것이 아니라 **잘못된 검증 문제를 체계적으로 최적화하는 것**이다.

이미 좋은 부분은 유지해야 한다. 이미지당 출력 하나, 불량 양성 클래스, 원본 보존, 원격 추론 API 금지, 정확한 가중치 버전, ID 정렬, 같은 holdout 및 OOF 출처, 전체 검증 예측의 AUROC, 실패 기록, 고정 가중치 재현과 재학습의 구분이 명시되어 있다. 단일 수직 실행 경로를 먼저 만들고 대형 프레임워크를 보류한 판단도 현재 범위에 맞는다.

**필수 추가 항목은 연구 질문·가설 기록, 질문별 EDA와 이미지 카탈로그, 검증의 대상·한계 결정, 파생 데이터의 식별 계약, 작고 공정한 선택 절차, 복구·최종 선택의 영수증이다.** Feast, FiftyOne, Hydra, Lightning, DVC를 모두 도입할 이유는 확인되지 않았다.

## 첫 본학습 전에 해결할 사항

### F01 · P0 · 가설이 양식의 빈칸에 머물고 실행 순서를 통제하지 않는다

**근거:** `docs/PLAN.md:62–66`에는 질문·가설·판정 규칙이 있고 `reports/WRITING-PLAN.md:5–14`에도 연구 질문이 있다. 그러나 `experiments/BACKLOG.md:7–13`은 시스템 측정과 모델·학습률 비교로 바로 시작하며, `experiments/CARD-TEMPLATE.md:6–12`는 가설의 예측·반증 기준·관측 단위를 분리하지 않는다.

**실패 방식:** “해상도를 높이면 좋아지는가?”만 남기면 결과가 나온 뒤 배경·작은 결함·모델 용량 중 편한 설명을 붙이기 쉽다. 데이터가 작은 결함 가설을 지지하지 않아도 예정된 모델 실험을 그대로 소비하게 된다.

**작은 수정:** 본학습 앞에 연구 준비 항목 하나를 둔다. 질문마다 `관측 사실 → 가능한 설명 → 반증 가능한 예측 → 비교 대상 → 주지표/오류 관측 → 비용 한도 → 채택·보류 규칙`을 짧게 적는다. 가설은 예상한 방향뿐 아니라 예상이 틀린 경우 무엇을 배울지도 포함한다. 수치 기준은 데이터·P000 실측 후 실행 전에 고정할 수 있다. 연구 근거 카드와 실험 카드를 중복 장문으로 만들 필요는 없다.

**통과 확인:** 첫 모델과 첫 비교 실험에 “왜 이것을 실행하는가, 어떤 결과면 설명을 버리는가, 다음 행동은 무엇인가”가 결과를 보기 전에 적혀 있다. 관측되지 않은 결함 크기·제품 유형을 사실처럼 쓰지 않는다. 이 문서 아래의 가설 예시는 채택된 가설이 아니라 초안이다.

### F02 · P0 · 파일 무결성 검증 뒤의 EDA와 의미 검증이 빠져 있다

**근거:** `docs/PLAN.md:35`는 CSV·이미지 대응과 라벨·출력 검사를 목표로 한다. 실제 `scripts/verify_data.py:13–35`는 파일 목록·크기·SHA-256·추가 파일만 검사한다. `data/manifests/image-profile.json:2`는 픽셀 디코드가 없음을 명시한다. EDA는 `docs/PLAN.md:48–56`에 방향만 있다.

**실패 방식:** 원본과 똑같은 파일이라는 사실이 “이미지 디코딩이 성공한다, 라벨과 이미지가 올바르게 결합된다, 색상 처리와 방향이 일관된다, 결함이 resize 뒤에도 남는다”까지 증명하지 않는다. 학습 때 처음 발견한 이미지 오류나 잘못된 경로 결합은 Colab 예산을 낭비한다. 전체 점수만 보면 배경·제품 유형과 라벨의 상관을 결함 학습으로 오해할 수 있다.

**작은 수정:** 원본은 그대로 두고 이미지 ID를 키로 한 작은 카탈로그와 질문별 EDA 기록을 만든다. 전수 CPU 디코드·CSV 대응·허용 라벨·경로·고유 ID 검증과, 표본 시각 검토를 구분한다. 카탈로그에는 원본 상대 경로·해시·train/test 역할·원본 라벨·실제 디코드 크기/모드·디코드 상태를 기본으로 둔다. 표본 조사에는 표본 추출 방법·시드·선택 ID·관측 태그·불확실성을 남긴다. 원본 라벨을 사람이 덮어쓰지 않는다.

최소 EDA 질문과 필요한 결정은 다음과 같다.

| 질문 | 조사·산출물 | 그 결과로 결정할 것 |
|---|---|---|
| 파일을 같은 방식으로 읽을 수 있는가? | 전수 디코드, CSV 대응, 모드·방향·손상 목록 | 공통 디코더와 오류 처리; 조용한 샘플 누락 금지 |
| 크기·색상·배경과 클래스가 얽혀 있는가? | 학습 라벨별 크기 표, 각 크기·클래스의 표본 원본 | 혼동 요인과 오류 분석 slice; 메타데이터 진단의 필요성 |
| 제품 배치와 눈에 보이는 결함은 어떠한가? | 단일/복수 제품·시각적 결함 후보의 표본과 불확실 태그 | 전체 이미지 입력, 해상도, 허용 증강 후보 |
| 전처리가 판단 정보를 없애는가? | 동일 이미지의 원본·resize/pad/후보 증강 비교 | 기준 전처리와 보류할 크롭·색상 변환 |
| 독립 표본 가정이 타당한가? | 근접 중복 후보와 사람이 확인한 관계 기록 | 그룹 분할과 남는 누수 불확실성 |
| 관측된 train/test 형태 차이에 대응할 근거가 있는가? | 현재 알려진 비율·해상도 차이, 학습 이미지의 변환 민감도 | 검증의 한계와 사전에 정한 보조 스트레스 평가 |

마지막 항목은 테스트 라벨·외부 원본을 찾으라는 지시가 아니다. 제공 규정은 정답 없는 테스트 이미지의 일반적인 메타데이터·시각 EDA를 명시적으로 금지하지 않으며, 이를 위한 별도 승인 절차를 추가할 이유는 없다. 이런 관찰은 테스트 통계로 정규화·PCA·클러스터를 학습하거나 모델을 적응시키는 행위와 구분한다. 학습되는 변환은 학습 부분으로 범위를 고정하고, transductive adaptation을 제안한다면 규정 적합성·검증 방법·정보 사용 범위를 별도로 설명한다.

**통과 확인:** CPU 검사에서 10,821개 학습 ID와 800개 테스트 ID의 대응·디코드가 설명되고, 각 EDA 질문에 관측 또는 “미확인”이 있으며 적어도 분할·전처리·첫 모델의 결정과 연결된다. 이상 파일이 있다면 제외를 숨기지 않고 파생 목록과 이유를 기록한다.

### F03 · P0 · holdout이 무엇을 검증하는지 아직 정해지지 않았다

**근거:** `docs/PLAN.md:48–54`는 형태 차이와 그룹 분리 필요성을 인식하지만 약 80/20 holdout은 후보 단계다. `docs/COLAB.md:9–13`의 train/test 형태 차이는 크다. `experiments/BACKLOG.md:22`의 그룹 누수 실패 검사에는 그룹의 생성 근거와 미확인 관계의 처리 계약이 없다.

**실패 방식:** 같은 촬영 개체의 유사 이미지가 양쪽에 들어가면 점수가 낙관적이다. 반대로 “같은 제품 종류” 전체를 무조건 같은 그룹으로 묶으면 실제 목표와 다른 미관측 제품 일반화 문제를 만들 수 있다. 학습 분포 내부 holdout에서 해상도 증가가 좋아도 정사각형 테스트에 대한 개선이 보장되지는 않는다.

**작은 수정:** 분할 전에 평가 대상 문장을 한 줄 정한다. 예: “제공 학습 분포에서 독립 촬영 단위에 대한 이미지 분류를 추정하며, 테스트 분포 대표성은 미확인이다.” 제품 종류와 동일 촬영 개체/연속 촬영 그룹을 별개 필드로 취급한다. 해시·perceptual hash·임베딩 유사도는 **관계 후보를 찾는 수단**이며 파일명·해상도·유사도 하나만으로 개체를 확정하지 않는다. 확인한 그룹과 근거, 그룹 연결 규칙·버전을 보존하고 부모 이미지에서 만든 모든 파생물은 부모와 같은 split을 상속한다.

주 검증은 클래스 수와 그룹 독립성을 고려해 고정한다. 테스트 구조를 모른다는 문제는 다른 split 이름으로 숨기지 않는다. 필요하면 학습 검증 이미지의 label-preserving 변환 민감도를 보조 평가하되 “테스트를 재현했다”고 주장하지 않는다. 결함이 사라지는 크롭은 원래 라벨로 같은 검증을 구성하면 안 된다.

**통과 확인:** 각 split의 ID·그룹·클래스 수·생성 규칙·해시가 저장되고, 동일 원본/확인된 종속 그룹/파생 이미지의 교차가 0이다. 미확인 관계와 test 대표성의 한계가 명시된다. AUROC를 계산할 양쪽 클래스가 존재하며, 그룹 때문에 이것이 불가능하면 분할 정책을 다시 결정한다. 완전한 누수 부재를 증명했다고 쓰지 않는다.

### F04 · P0 · 첫 backbone에도 사전학습 가중치 승인 근거가 필요하다

**근거:** `research/competition-rules.md:24–27`에는 공개 시점·라이선스·외부 이미지·원격 추론 제한이 있다. `research/CARD-TEMPLATE.md:4–13`은 좋은 확인 양식이다. 그러나 `experiments/BACKLOG.md:12`에서 명시적인 확인은 두 번째 backbone 항목에 나타나며 첫 모델은 미정이다(`docs/PLAN.md:26`).

**실패 방식:** 라이브러리의 편리한 `pretrained=True`가 시간이 지나 다른 checkpoint를 받거나, 모델 코드의 라이선스만 확인하고 실제 가중치의 조건·공개일을 놓칠 수 있다. 첫 baseline을 나중에 규정 때문에 버리면 모든 비교의 기준이 흔들린다.

**작은 수정:** 첫 학습과 첫 임베딩 추출 전에 동일한 간단한 gate를 적용한다. 모델 코드·정확한 가중치 식별자/파일 해시·출처·공개일 근거·가중치 사용 조건·기본 입력 변환을 기록한다. P000에서도 실제 사용할 가중치를 특정한다. 사용자에게 별도 도구 승인을 묻는 절차가 아니라 연구자가 규정을 확인하는 기록이다. 허용 가중치에서 이미 학습된 지식과 외부 이미지를 새로 추가 학습하는 행위를 구분한다.

**통과 확인:** 첫 baseline과 임베딩 encoder 각각에서 위 근거를 찾을 수 있다. 최종 실행기는 가중치의 정확한 버전을 불러오며 조용히 최신 모델로 대체하지 않는다. 사용자가 제공한 규정의 공개 시점은 **2026-11-15까지(당일 포함)**다. 연구 카드의 “2026-11-15 이전”은 “2026-11-15까지”로 맞춰야 한다. 이미 제공된 기준을 다시 주최 측에 확인할 필요는 없다.

### F05 · P0 · 이미지 단위 라벨을 보존하는 입력·출력 계약이 더 구체적이어야 한다

**근거:** `README.md:18–21`, `research/data-description.md:5–23`에 이미지 단위 라벨이 있다. `docs/PLAN.md:55–56`은 크롭의 라벨 오류를 인식한다. 그러나 전처리·head·loss·확률 변환의 실제 스키마는 없고 `docs/PLAN.md:125`는 출력 범위 검사만 제안한다.

**실패 방식:** 이미지 불량 라벨을 모든 crop에 붙이면 정상 패치가 양성이 된다. 여러 제품 중 어떤 조건에서 이미지가 불량인지 제공 설명만으로 확정할 수 없다. RGB/BGR, EXIF 방향, 보간법, padding, normalization, train/eval transform, sigmoid 적용 횟수가 달라져도 숫자는 0~1에 들어갈 수 있다. 여러 view의 예측을 이미지 단위로 합치지 않으면 샘플 수와 지표도 틀어진다.

**작은 수정:** 첫 baseline은 근거가 마련된 전체 이미지 경로로 시작하고, 디코더부터 최종 불량 확률까지 한 계약으로 기록한다. 예를 들어 1-logit head와 `BCEWithLogitsLoss`를 택한다면 sigmoid는 평가 출력에서 한 번만 적용하고 클래스 1과의 관계를 검사한다. 이는 특정 구현의 강제가 아니라 명시성의 예다. resize/pad·정규화·증강 범위·평가 변환·집계 순서·FP32 지표 계산 여부를 설정에 담는다. 크롭/MIL·TTA는 별도 가설과 비용으로 취급하며 위치 라벨이 있는 것처럼 다루지 않는다.

**통과 확인:** 작은 고정 이미지 집합이 학습 검증 경로와 별도 `validate/predict` 경로에서 같은 평가 입력·점수를 낸다. 배치 순서가 바뀌어도 ID별 결과가 같다. 여러 view를 쓰면 view→부모 ID 집계 뒤 정확히 이미지당 한 행이 나온다. 가짜 완벽/역전 예측으로 양성 클래스와 AUROC 방향을 검사한다.

### F06 · P1 · 첫 기준 학습의 최적화·상태 복구 계약이 아직 비어 있다

**근거:** `docs/PLAN.md:37`, `70–75`, `114`는 설정·epoch 복구를 요구한다. `docs/COLAB.md:23–31`에는 측정과 mixed precision 대응이 있지만, optimizer·scheduler·유효 batch·모델 선택 시점 등 실제 실행 의미는 정하지 않았다. 이는 실행기 구현 전에 결정해야 할 내용이다.

**실패 방식:** AMP, gradient accumulation, 배치 축소, scheduler의 step 단위가 바뀌면서 서로 다른 실험을 같은 설정으로 보고할 수 있다. sampler 재가중과 loss 재가중을 동시에 넣으면 불균형 보정을 이중 적용한다. “last 저장”만으로 scheduler·RNG·sampler·scaler가 복원됐다고 보장할 수 없다.

**작은 수정:** 보수적인 baseline 한 개의 실제 설정을 고정한다. optimizer와 weight decay, 학습률, scheduler와 update 단위, warmup 여부, batch/accumulation/유효 batch, epoch 또는 optimizer step 예산, head/backbone freeze 여부, AMP dtype·지원 실패 대응, early stopping과 best 선택 지표·동점 규칙을 포함한다. 첫 불균형 처리는 명시적인 단순 기준으로 시작하고 sampler·loss 변경은 근거를 가진 별도 비교로 한다. 랜덤 시드뿐 아니라 데이터 순서와 epoch 경계의 저장 의미를 기록한다.

**통과 확인:** 작은 합성 데이터의 end-to-end 검사 외에 제공 학습 부분의 작은 표본에서 loss/gradient/확률이 유한하고 학습이 반응하는지 확인한다. 이 표본 과적합 점수를 일반화 결과로 쓰지 않는다. 같은 환경에서 중단 없는 짧은 실행과 epoch 경계 재개 실행의 step 수·scheduler·상태 및 예측 차이를 비교한다. “재개 가능”과 “중단 없는 학습과 수치상 동등”을 별도 결과로 기록한다.

## 튜닝·모델 확장 전에 해결할 사항

### F07 · P1 · 이미지 카탈로그와 파생 feature/cache의 식별 계약이 없다

**근거:** `README.md:37–50`에는 manifest와 splits만 있고 이미지별 조사·파생 특징의 역할은 없다. `docs/ARCHITECTURE.md:15–27`은 원본에서 split·학습으로 바로 이어진다. `.gitignore:16–18`은 파생 파일을 제외하지만 파생 파일의 원천·변환·버전 기록 위치는 정하지 않는다.

**실패 방식:** 임베딩 행 순서가 CSV와 달라지거나 encoder·resize가 바뀌어도 같은 캐시를 읽을 수 있다. 검증 이미지를 사용해 fine-tune한 encoder의 특징을 OOF처럼 쓰거나 전체 데이터로 PCA/표준화를 학습하면 평가에 정보가 섞인다. 캐시가 사라지면 논문 그림이나 근접 중복 조사의 근거를 복원하기 어렵다.

**작은 수정:** 필요한 것은 우선 이미지 카탈로그와, **실제로 캐시할 때만** 적용하는 작은 manifest다. 파생물별로 부모 데이터 manifest/ID·정렬 순서·라벨과 split 버전·변환 코드/설정 해시·encoder checkpoint/입력 전처리·출력 shape/dtype·파일 해시·생성 run을 기록한다. 학습된 변환은 fitting에 사용한 ID/split을 기록한다. 고정된 허용 pretrained encoder의 독립 이미지 추출과 데이터에서 학습한 PCA·정규화·fine-tuning을 구분한다. 모델에 넣지 않는 EDA 임베딩도 그 용도를 표시한다.

훈련 때의 무작위 증강을 단일 고정 캐시로 대체하면 원래 실험이 달라진다. 캐시 대상으로 삼는 것은 재사용 가치가 있는 결정론적 resize·메타데이터·임베딩 등으로 제한하고, 캐시의 비용이 작은 모델을 곧바로 학습하는 비용보다 큰지도 본다.

**통과 확인:** 입력 해시·전처리·encoder·fitting scope 중 하나를 바꿨을 때 기존 캐시 사용이 거절된다. ID의 중복·누락·재정렬을 탐지한다. 저장 위치를 옮겨도 상대 경로와 manifest로 재생성할 수 있다. fine-tuned 특징을 쓰는 검증이면 해당 행의 학습 제외 근거가 있다.

**도구 판단:** Feast는 batch/offline과 online feature 관리를 모두 지원하므로 “표 데이터 실시간 서빙 전용”이라고 배제하면 부정확하다. 다만 그 기능을 설치하는 것만으로 이 대회의 라벨 버전·촬영 그룹·검증 분할 계약이 생기지는 않는다. 현재는 단일 연구자·정적 이미지·제출 CSV 범위이므로 작은 카탈로그와 캐시 manifest가 먼저라는 설계 판단이다. [Feast 공식 개요](https://docs.feast.dev/).

FiftyOne은 임베딩 탐색·유사도·중복 후보 검토에 도움이 될 수 있는 선택지다. 기존 임베딩을 연결하는 식으로도 사용할 수 있지만, 유사도를 실제 촬영 그룹의 정답으로 취급해서는 안 된다. 표본 contact sheet와 간단한 후보 목록으로 충분하면 GUI 도입은 미룬다. [FiftyOne Brain 공식 문서](https://docs.voxel51.com/brain/index.html).

### F08 · P1 · 작은 HPO에도 비교의 공정성과 예산 정산 규칙이 필요하다

**근거:** `docs/PLAN.md:88–93`은 2~3개 후보·같은 epoch/조기 종료·추가 seed를 제안한다. `experiments/BACKLOG.md:9–12`는 학습률→입력→loss→backbone의 순서다. `experiments/CARD-TEMPLATE.md:11–12`는 예산·판단 기준의 빈칸만 있다.

**실패 방식:** 같은 epoch는 같은 계산량이 아니며, 같은 wall time도 같은 최적화 기회를 뜻하지 않는다. 입력 크기를 늘리며 batch를 줄이면 해상도 효과와 optimization 효과가 섞인다. 무거운 후보만 조기 중단되거나 마지막 seed 하나를 보고 선택하면 “더 좋은 모델”이라는 결론이 과장된다. 순차 변경은 비용을 줄이지만 학습률×해상도 등 상호작용을 놓칠 수 있다.

**작은 수정:** P000 뒤 한 장짜리 예산표를 만든다. 준비·학습·검증·저장·추론·복구·리허설 시간을 포함하고 후보별 실제 GPU 시간을 기록한다. 비교 목적에 따라 `같은 학습 기회(epoch/step)`인지 `같은 자원 예산`인지 명시한다. batch/accumulation 변경은 숨기지 않는다. 비교 후보는 같은 split·paired seed와 같은 선택 규칙을 쓰며, 아키텍처 간에 서로 맞지 않는 학습률 하나를 강제하지 말고 제한된 동등한 탐색 기회를 준다. OOM을 자동 해결하며 설정을 바꿨다면 새 설정·run으로 남긴다.

최초 가설에 맞춰 한 변수 비교를 우선하되, 유망 후보에서 명확한 상호작용 하나만 후속 확인한다. 전체 grid나 최적 조합 보장을 요구하는 것은 아니다. 성능이 비슷하면 더 싸고 단순한 모델을 고르는 기준을 사전에 둔다.

**통과 확인:** 후보·범위·순서·run/시간 상한·early stopping·best 선택 규칙이 실행 전에 저장된다. 보고서 표에서 계획 예산과 실제 epoch/step·GPU 시간이 구분된다. 실패·중단 비용을 합계에서 빼지 않는다. 예산을 다 쓰기 전에 최종 재현·추론 몫을 확보한다.

### F09 · P0 · holdout 반복 선택의 낙관 편향을 인정하지만 제한 장치가 늦다

**근거:** `docs/PLAN.md:92–93`은 추가 확인을 “대규모 튜닝 전에” 정하도록 한다. 그러나 크기가 작은 튜닝도 best epoch, 여러 입력·loss·backbone, ensemble 가중치까지 같은 holdout을 반복 사용할 수 있다. `reports/WRITING-PLAN.md:38`은 근소한 차이를 과장하지 말라고 하지만 불확실성 산출 절차는 없다.

**실패 방식:** 같은 검증셋을 수십 번 보고 가장 높은 값 하나를 보고하면 seed 변동·유한 표본 오차·선택 편향이 모두 감춰진다. 일반 bootstrap 구간 하나로 이 선택 편향이 교정됐다고 말할 수도 없다.

**작은 수정:** E002 전에 최종 확인 정책을 정한다. 무료 예산에서는 모든 후보의 nested CV를 강제할 필요가 없다. 예를 들어 탐색 holdout을 고정하고, 최종 1~2개만 사전 지정한 추가 seed 또는 독립성에 근거한 추가 split으로 확인하며, 가능하면 최종 확인용 데이터를 반복 선택에 쓰지 않는다. 추가 seed는 optimization 변동을 확인할 뿐 같은 holdout의 선택 편향을 없애지 않는다고 명시한다. 별도 확인 예산이 없으면 그 사실과 모든 선택 횟수를 기록하고 결론의 강도를 낮춘다.

같은 검증 ID에 대한 후보 차이는 paired 방식으로 비교하고, 종속 그룹이 있으면 그룹 단위 재표집을 고려한다. 클래스 없는 재표집은 무효로 처리한다. AUROC 외 PR-AUC·slice별 오류 같은 보조 지표는 진단용이며 공식 지표를 몰래 바꾸지 않는다. slice의 표본 수와 양쪽 클래스 유무를 함께 표시한다. 확률을 출력하더라도 AUROC 상승을 확률 보정 개선으로 해석하지 않는다.

**통과 확인:** 모델·epoch·가중치 선택에 사용한 모든 검증과 최종 확인 검증의 역할이 기록된다. 비교표는 한 번의 최대값만 보여주지 않으며, 반복 seed 결과 또는 확보하지 못한 한계를 남긴다. “유의한 개선”은 그 표현을 지지하는 방법·가정이 있을 때만 쓴다. 최종 확인을 보고 다시 바꾼 모델은 이미 그 확인 데이터를 선택에 사용한 것으로 표시한다.

### F10 · P1 · 앙상블 규칙은 대체로 맞지만 가중치 선택과 최종 재학습 관계가 더 필요하다

**근거:** `docs/PLAN.md:99–106`의 미학습 예측·ID·split 검사·가중치 고정은 적절하다. `docs/PLAN.md:130`도 전체 데이터 재학습과 검증 모델을 구분한다. 다만 가중치 탐색 횟수, selection bias, OOF에서 최종 test 예측으로 넘어가는 recipe는 아직 없다.

**실패 방식:** 같은 holdout에서 모델을 고르고 가중치를 촘촘히 최적화한 뒤 같은 점수를 “확인된 앙상블 향상”으로 보고할 수 있다. OOF 평가와 test 추론이 다른 fold 집계·재학습 모델로 바뀌면 검증한 조합과 제출한 조합의 관계가 사라진다. 서로 다른 오류를 낸다는 말만으로 ensemble 향상을 보장할 수는 없다.

**작은 수정:** 단순 평균을 첫 기준으로 유지한다. 가중 평균은 후보 수를 작은 사전 집합으로 제한하고 단일 최선·단순 평균 대비 차이와 추론 비용을 함께 본다. 조합 manifest에 각 예측 행의 모델 학습 출처, 구성원별 전처리·확률 변환, 이미지/view/fold/model 집계 순서를 둔다. CV를 도입할 때만 OOF 행별 fold 모델을 요구한다. 전체 데이터 재학습을 택하면 epoch 등 최종 학습 길이를 어떻게 정할지 검증 단계에서 결정하고, 검증 모델의 점수를 재학습 모델의 직접 측정값으로 붙이지 않는다.

**통과 확인:** 모든 검증 행에서 모든 구성원이 해당 이미지/종속 그룹을 학습에 사용하지 않았음을 검사한다. 가중치 선택에 쓰인 평가와 추가 확인 결과를 구분한다. 조합 파일 하나로 고정 구성원 로딩→ID 정렬→동일 집계→800행 출력이 재생성된다. 향상 근거가 약하면 단일 모델 선택도 성공적인 결론으로 남긴다.

## 첫 장시간 실행부터, 늦어도 제출 전에 해결할 사항

### F11 · P0 · 선택 기록의 저장 위치와 Git ignore 정책이 충돌할 수 있다

**근거:** `submissions/README.md:3`은 파일 해시·생성 run·실제 선택 파일을 기록하도록 하지만 위치를 정하지 않는다. `.gitignore:19–22`는 `models/`와 `submissions/` 아래 README 이외의 모든 파일을 제외한다. `docs/PLAN.md:104`, `113`, `124–130`은 고정 조합·최종 선택 manifest를 요구한다.

**실패 방식:** `submissions/final.json`이나 `models/registry.json`을 자연스러운 위치에 만들면 Git이 기본적으로 무시한다. 코드와 문서는 남아도 실제 선택한 가중치·CSV·recipe를 나중에 찾을 수 없다. W&B alias가 바뀌거나 로컬 VM이 사라지면 복구도 어렵다.

**작은 수정:** 바이너리·예측 CSV는 계속 제외하되 작은 run 결과, 모델·조합·제출 선택 기록의 추적 위치를 하나 정한다. 필요하면 JSON/manifest만 allowlist하거나 추적되는 `experiments/results/` 같은 위치를 쓴다. 실제 제출 기록은 로컬 생성과 플랫폼 업로드·최종 선택을 구분한다. 수정 이력 또는 append-only 선택 이력으로 직전 결정을 덮어쓰지 않는다.

**통과 확인:** 최종 선택 manifest가 `git ls-files`에 실제 나타난다. manifest에서 코드 commit·실제 설정·split·preprocess·가중치/복구본·검증 예측·테스트 예측·출력 CSV 해시까지 따라갈 수 있다. 모델/ensemble을 바꾸면 새 선택 기록이 생긴다. 최종 제출 파일의 hash와 플랫폼에서 선택된 파일의 식별자가 연결된다. 대회 제출은 여전히 사용자 명시 지시가 있어야 한다.

### F12 · P0 · Colab 종료와 W&B/Drive 저장 사이의 실패 계약이 없다

**근거:** `docs/PLAN.md:110–118`은 계정 비공개 범위·저장량·best/last·복구본·API key를 잘 구분한다. `docs/COLAB.md:17`, `25–26`은 세션 종료와 복구 실측을 요구한다. 하지만 로컬 저장 완료·복사 완료·Artifact 업로드 완료의 구분과 offline fallback 조건은 없다.

**실패 방식:** `run.log`나 upload 요청 뒤 UI에 run이 보인다고 가중치가 영속 저장됐다고 생각하면, 세션 종료 때 유일한 best/last가 사라질 수 있다. `last` 덮어쓰기 중 종료되면 재개 파일이 손상될 수 있다. Drive에 복사됐어도 hash를 확인하지 않았다면 복구 가능한 파일인지 모른다.

**작은 수정:** 로컬에서는 임시 파일 저장 후 검증·원자적 이름 교체를 하고, 원격 저장은 목적지 파일의 완료·해시를 확인한 뒤 “복구 가능”으로 표시한다. W&B 기록과 학습 상태의 authoritative copy를 구분한다. API 실패·네트워크 장애 시 로컬 결과/미동기화 상태를 보존하고 다음 세션에서 중복 없이 연결할 방법을 정한다. 무료 저장량을 추측하지 말고 실제 계정 접근·quota·최종 artifact 다운로드를 확인한다. 성능 측정에는 저장·업로드 대기도 포함한다.

epoch 경계 저장이면 최대 한 epoch의 손실이 허용 가능한지도 P000에서 본다. epoch가 가용 세션에 비해 너무 길 때만 더 자주 저장하는 복잡도를 검토한다. “매번 모든 가중치 영구 업로드”는 필요하지 않다.

**통과 확인:** 첫 장시간 run 전에 새 세션이 Drive 또는 W&B에서 checkpoint를 내려받아 해시를 확인하고 재개/평가한다. 업로드가 끝나기 전에는 `completed-and-durable`로 기록하지 않는다. 네트워크 없는 짧은 기능검사 후 로그·산출물을 복구한다. 토큰 없이도 최종 평가자가 필요한 파일과 설치 절차를 받을 수 있는 제출 경로가 있다. W&B 계정 연동 자체는 이번 검토에서 하지 않았다.

### F13 · P0 · 재현의 세 수준은 좋지만 실제 합격 기준과 이식성 묶음이 남아 있다

**근거:** `docs/PLAN.md:120–130`은 파일·고정 가중치·재학습을 명확히 나눈다. `docs/PLAN.md:128`은 P000의 반복 평가로 허용오차를 정하도록 한다. `research/competition-rules.md:31–40`과 `research/course-notice.md:60–64`는 학습부터 추론 코드·가중치·환경 제공을 요구한다. 현재 환경/lock 파일·진입 notebook은 아직 없다.

**실패 방식:** 초기 backbone의 수치 오차만으로 다른 최종 backbone·AMP·TTA·ensemble의 허용오차를 정하면 부적절할 수 있다. seed 하나를 고정해도 독립 학습 결과의 동일성은 증명되지 않는다. 고정 가중치가 재현되어도 checkpoint의 원래 학습 과정을 완전히 재현한 것은 아니다. 개인 Drive 절대 경로나 인증된 모델 다운로드에 의존하면 평가자의 새 환경에서 실패한다.

**작은 수정:** P000에서는 측정 방법과 허용오차 정책을 정하고, 최종 사용 예정 추론 경로의 같은 가중치 반복 평가로 타당성을 확인한다. 최종 선택 이전에 수치를 고정하며 실패 후 무단 완화하지 않는다. 파일 해시는 바이트 동일성, 행별 예측 차이·AUROC 차이는 수치 재현성으로 따로 판정한다. CSV의 수치 허용오차 통과가 항상 CSV 바이트 해시 동일을 뜻하지 않는다.

코드 commit·dirty diff 처리 정책·resolved config·Python/패키지 lock 또는 검증된 설치 목록·CUDA/cuDNN/GPU·precision·seed/결정론 옵션·전처리·가중치 위치를 묶는다. 상대 경로 인자를 받고 학습/추론 실행을 분리한다. 최종 제출용 추론이 불필요한 사전학습 파일을 다시 인터넷에서 받지 않게 한다. 학습 재실행은 예산에 맞는 짧은 절차 검사와 가능하면 선택된 설정의 독립 run을 구분하며, 전체 재학습을 실제로 하지 않았다면 했다고 쓰지 않는다.

**통과 확인:** 빈 새 세션에서 문서만 따라 설치·데이터 검증·선택 가중치 로드·검증 AUROC/행별 비교·800행 예측·ensemble 재현을 실행한 기록이 있다. 사용한 설치 버전과 가중치가 실제 기록과 같다. 학습 재실행 여부, 중단 복구 여부, 고정 가중치 재현 여부가 세 별도 항목으로 보고된다. 규정이 보장하지 않은 “다른 GPU에서도 비트 단위 동일”을 요구하거나 약속하지 않는다.

### F14 · P1 · 마감 직전 리허설과 미확정 제출 조건이 운영 위험이다

**근거:** `docs/PLAN.md:163–167`은 대회 종료 전날 리허설을 제안한다. `docs/PLAN.md:27`은 공식 URL·선택 파일 수·제출 형식이 미정이고, `research/competition-rules.md:3`, `35`, `44`는 전달된 규정·별도 공지·하루 3회 제한을 기록한다. 기술보고서는 `research/course-notice.md:16`, `25–29`에 따라 12월 8일 마감·평가 65%다.

**실패 방식:** 무료 GPU가 마지막 날 잡히지 않거나 제출 패키지 설치가 실패하면 새 모델을 버리는 것만으로 해결되지 않는다. 코드 제출이 종료 후라고 해서 최종 가중치와 recipe 준비를 종료 뒤로 미룰 수도 없다. 보고서가 큰 평가 비중인데 탐색에 전부 소비하면 실패 원인·모델 선택 근거가 사후 기억에 의존한다.

**작은 수정:** 첫 유효 baseline 직후 작은 재현 리허설을 한 번 하고, 예산과 달력에 탐색 중단 시점을 둔다. 예를 들어 11월 27일까지 실행 가능한 fallback과 첫 완전 리허설, 28~29일에는 최종 선택·재현·복구, 30일 10:00 이전에는 승인된 선택 파일 확인을 목표로 삼을 수 있다. 이는 교수 요구가 아니라 무료 Colab 위험을 감안한 제안이다. 공식 공지의 최신 URL/내용·제출 방식·가중치 전달 경로·선택 파일 수·기준 시간대를 확보한다.

하루 제출 상한을 채우는 것을 실험 목표로 삼지 말고, 로컬 근거가 있는 몇 개의 제출과 실제 선택 기록만 관리한다. Public은 30%, Private는 70%이며 최종 순위는 Private 100%라는 전달 규정을 유지한다. Public을 tuning loop의 무제한 oracle로 사용하지 않는다. 자동 제출이나 GPU 결제는 추가하지 않는다.

**통과 확인:** 마지막 탐색 전에 이미 재현 가능한 fallback이 영속 저장돼 있다. 추가 학습 없이 최종 선택을 제출 형식으로 다시 만들 수 있다. 11월 30일 10:00~12월 1일 10:00 코드 제출과 12월 8일 23:59 보고서를 별도 체크한다. 최신 공지에 따라 변경한 사항은 출처·확인일을 남긴다.

### F15 · P1 · 보고서 자동화에는 결과표 외에 주장·실패·관측의 계보가 필요하다

**근거:** `reports/WRITING-PLAN.md:14`, `23–38`, `44–50`에는 주장 연결·실패·실제 결과라는 좋은 원칙이 있다. 하지만 자동 그림 목록(`30–36`)에는 EDA와 오류 사례의 표본 선택·가설 결과가 없고, 실험 카드(`experiments/CARD-TEMPLATE.md:22–23`)에는 관측과 설명의 증거 수준을 나누는 칸이 없다.

**실패 방식:** “고해상도가 작은 결함을 더 잘 보았다”를 AUROC 상승만으로 주장하거나, 이긴 모델에 유리한 오류 사진만 고를 수 있다. 여러 변경을 한 최종 모델과 baseline 차이를 개별 방법의 효과로 분해해 설명할 수도 있다. 실패 run을 보존해도 무엇을 배웠는지 없으면 연구 서사가 되지 않는다.

**작은 수정:** 핵심 주장별로 `가설 ID / 비교 run 집합 / 데이터·split·평가 프로토콜 / 표·그림 생성 입력 / 관측 / 해석 / 반례·한계`의 짧은 행을 둔다. EDA 그림과 오류 사례는 선택 기준·ID를 보존하고, 주지표·사전 정의 slice·오분류 후보를 구분한다. threshold 기반 오류를 보일 때 threshold 선택 근거를 기록한다. 소수 샘플의 heatmap이나 시각 예시는 정량적인 원인 증명이 아니라 설명용 증거다.

실패는 시스템 실패(OOM·중단·데이터 오류)와 완료했으나 가설이 지지되지 않은 실험을 구분한다. 후자는 보고서에서 중요한 결과다. 모델·가중치·코드의 인용은 원문과 실제 채택한 설정에 연결하고, 과거 tabular 대회 경험을 이 이미지 데이터에서 입증된 전략처럼 인용하지 않는다.

**통과 확인:** 대표 주장 하나를 표·그림→예측→checkpoint→config/code→split/data까지 역추적할 수 있다. 같은 질문에서 실패한 완료 실험과 OOM/중단 내역도 찾을 수 있다. 불확실성을 측정하지 못했다면 문장에 한계를 적고, “왜 좋아졌는지”를 확인하지 못한 경우 원인으로 단정하지 않는다. 계획·측정·추정을 표에서 혼동하지 않는다.

## 최소 수정 실행 순서

이 순서는 새 플랫폼 도입 계획이 아니라 기존 작은 Python 실행 경로 앞뒤에 필요한 결정을 보완한 것이다.

1. **문제와 규정 고정:** 이미지당 불량 확률·공식 AUROC·개인/무료 Colab 예산·마감·금지 사항을 정리한다. 미확정 제출 정보는 질문 목록으로 남긴다.
2. **연구 질문·초기 가설:** 데이터에서 무엇을 알아야 모델을 선택할 수 있는지 적는다. 관측하지 않은 내용은 가정으로 표시한다.
3. **원본 검증→EDA→카탈로그:** 해시 검증과 의미/디코드 검증을 나누고, 학습 데이터의 표본·관계 후보·전처리 비교를 기록한다. 조사 결과에 따라 초기 가설을 수정하고 변경 이유를 보존한다.
4. **평가 대상·split·전처리 결정:** 확인한 종속 관계를 분리하고, train/test 형태 차이 때문에 추정할 수 없는 범위를 밝힌다. validation ID와 프로토콜을 고정한다.
5. **첫 모델·가중치·환경 결정:** 가중치 규정 확인, 가장 작은 타당한 기준 모델 설정, 필요할 때만 특징 캐시의 fitting scope와 버전 계약을 정한다.
6. **수직 구현과 기능검사:** train→validate→predict→checkpoint→reload→결과 JSON을 잇는다. ID/라벨 방향/누수/수치/재개 검사를 먼저 통과시킨다.
7. **P000과 baseline:** 실제 무료 Colab의 시간·메모리·저장·복구를 측정하고 예산을 확정한다. baseline을 남긴 즉시 새 세션 재현을 한 번 수행한다.
8. **오류 분석→제한된 가설 비교:** 가장 중요한 미해결 질문부터 2~3개 후보로 비교한다. 모든 백로그를 의무 실행하지 않는다. 동일 split·선택 규칙과 실제 계산량을 기록한다.
9. **소수 후보 확인→앙상블 여부 결정:** seed/추가 검증 정책에 따라 불확실성을 확인하고 단순 평균부터 평가한다. 확인이 약하면 단순한 모델을 선택한다.
10. **선택 freeze→최종 리허설·복구:** 최종 manifest·정확한 artifact 버전·환경·출력 해시·복구본을 고정하고 독립 세션에서 실행한다. 실제 대회 선택은 명시 승인과 기록을 거친다.
11. **실험과 병행한 보고서 완성:** 각 단계에서 Methods·관측·실패를 기록하고, 결과 확정 후 Abstract·Conclusion을 완성한다. 제출 후 공개된 Private 결과는 선택 시점의 근거와 섞지 않는다.

### 시작할 가설의 예시 — 아직 채택하거나 검증하지 않음

| 질문·가설 초안 | 관측/비교 | 반증·보류 조건 |
|---|---|---|
| H1: 기준 resize가 일부 이미지의 판별 정보를 지울 수 있다 | 학습 표본 전처리 비교 후 같은 split에서 해상도/비율 보존 후보 평가 | 시각적 근거가 없거나 정해 둔 개선/비용 기준을 충족하지 못하면 보류; 작은 결함의 실제 위치 라벨이 있다고 가정하지 않음 |
| H2: 배경·크기·제품 유형과 라벨의 상관이 검증 성능에 영향을 줄 수 있다 | 메타데이터·시각 표본·slice별 오류와 필요 시 저비용 메타데이터 기준모델 | 그런 상관을 확인하지 못하면 해당 설명을 약화; 상관만으로 누수나 원인을 확정하지 않음 |
| H3: 클래스 불균형 보정이 양성 순위를 개선할 수 있다 | 고정한 baseline loss와 한 가지 보정의 paired 비교 | AUROC·변동·비용 기준을 못 넘으면 보류; 양성 개수가 적다는 사실만으로 보정 필요성을 확정하지 않음 |
| H4: 두 후보의 오류 차이가 단순 평균의 개선으로 이어질 수 있다 | 동일 미학습 검증 ID의 두 예측과 단순 평균, 비용 비교 | 오류가 달라도 평균의 확인된 이점이 없으면 단일 모델 유지 |

H2의 진단 모델은 선택 사항이다. 실제 테스트 라벨·원본 조회나 테스트 라벨 추정 도구로 사용하지 않는다. 이 가설 예시는 구체 후보·효과 크기·시간 기준이 정해지기 전의 출발점이다.

## 지금 보류해도 되는 것

- **전면적인 feature store·상시 서버:** 현재는 원본/카탈로그/선택 기록/필요한 캐시 계약이 우선이다. 반복 데이터 갱신·다수 모델/사용자의 공유 특징·서빙 일관성 문제가 실제 생길 때 Feast 등을 재평가한다.
- **FiftyOne 전체 도입:** 표본·근접 중복 후보 검토가 파일 목록과 간단한 그림으로 어려워질 때 고려한다. 모델 zoo의 외부 이미지나 무허가 가중치를 편의상 가져오지 않는다.
- **Hydra·Lightning·DVC:** 실행기의 복잡도·중복·산출물 관리 문제가 실제로 드러날 때 선택한다. 도입 자체를 연구 관리 완료 증거로 삼지 않는다.
- **전 후보 다중 fold/nested CV·큰 HPO·stacking·세밀한 ensemble weight search:** 현재 자원에서는 질문이 분명한 단일 holdout 비교와 소수 확인이 우선이다. 완전한 통계 검증을 하지 못한 한계를 정직하게 남긴다.
- **객체 검출·결함 segmentation·MIL·전면 crop training:** 객체/위치 라벨이 없으므로 기존 이미지 라벨을 확장 해석하지 않는다. EDA가 필요성을 지지하고 별도 weak-label 집계·검증을 마련할 때 검토한다.
- **칼리브레이션·threshold 최적화:** 공식 지표는 AUROC다. 유한한 불량 확률을 내는 계약은 필수지만, 별도 보정으로 순위 성능이 좋아진다고 가정하지 않는다. 운영 threshold 요구는 현재 제공되지 않았다.
- **고급 보고서 UI·자동 논문 검색·대형 대시보드:** 실제 결과·근거 카드·표·정적 그림과 원고가 먼저다. 제출 형식이 확인되면 필요한 빌드만 추가한다.

## 남아 있는 질문과 가정

1. 공식 대회 URL과 최신 공지, 최종 선택 파일 수, 코드/가중치 제출 형식·전달 경로·시간대는 아직 확인되지 않았다. 전달된 규정 이상의 교수 요구를 만들어내면 안 된다.
2. 학습/테스트의 생성 관계·촬영 개체 ID·제품 유형·복수 제품에서 이미지 라벨을 정한 세부 기준은 제공 설명만으로 알 수 없다. 크기 8종/4종을 곧바로 제품 종류나 crop 규칙으로 해석하지 않는다.
3. 정답 없는 테스트의 메타데이터·시각 EDA와 비지도 통계 fitting·transductive adaptation은 같은 행위가 아니다. 일반적인 관찰에 새 승인 조건을 붙이지 않는다. 학습되는 변환은 학습 부분에 한정하고, 별도 적응을 검토할 때는 규정 적합성과 평가에 미치는 영향을 따로 설명한다. 외부 원본·테스트 정답 추정은 명백히 범위 밖이다.
4. W&B entity/project, 비공개 접근·quota·다운로드 접근성과 Drive 복구 위치는 미정이다. 계정 권한이 있는 사용자의 실제 연결 확인이 필요하다.
5. 무료 Colab의 실제 GPU·가용 시간·할당 반복 가능성, backbone/입력 크기의 비용, 전체 학습을 한 번 더 할 여유는 측정되지 않았다. 재학습·fold·추가 seed를 지금 고정 의무로 만들 수 없다.
6. 전체 데이터 재학습을 최종 제출에 쓸지, 검증에 사용한 모델을 그대로 제출할지는 선택 사항이다. 두 방식의 검증 근거와 시간·재현 부담을 비교해야 한다.
7. 최종 성능 향상 기준·수치 재현 허용오차는 아직 없다. 임의 숫자를 채우지 말고 P000 및 사전 정의한 절차로 결정한다.

## 검토 한계와 실행 역할 기록

이 검토는 설계와 현재 저장소의 정합성 검토다. 모델 성능·실제 Colab 용량·W&B 업로드 신뢰성·최종 제출 재현 성공을 확인한 보고서가 아니다. 제공 원본의 파일 해시와 CSV 기본 통계는 확인했지만 전체 픽셀 EDA·근접 중복 조사·label 품질 검증·학습 실험은 수행하지 않았다. 원본 외부 데이터셋·외부 정답·테스트 라벨을 찾거나 유추하지 않았다. Feast와 FiftyOne의 범위 설명은 링크한 공식 문서를 확인했으며, 해당 도구가 설치되거나 계정에 연결됐다는 뜻은 아니다.

요청된 검토 역할은 **`gpt-6-astra` / `high`**다. 이 문서에는 실행 호스트가 제공한 별도 모델·reasoning effort 영수증이 첨부되지 않았다. 따라서 요청된 역할을 기록할 뿐, 문서 내용으로 실제 런타임 모델·effort를 독립 증명하거나 존재하지 않는 실행 영수증을 만들지 않는다.
