# 기본 코드베이스·우리 구현 범위·대회 모델 관리 설계

2026-11-17 운영 기준: [운영 진입점](OPERATIONS.md) → [현재 상태](CURRENT-STATUS.md)에서 시작한다. 아래 본문은 구현 전 설계 의도·완료 조건의 이력이며 당시 상태나 제안 명령은 현재 실행 지시가 아니다. 실제 CLI는 [실행 가이드](RUNBOOK.md)와 소스·테스트를 따른다.

현재: 작은 Python 패키지·ResNet18 공통 경로·Colab 진입 notebook·로컬 장부/보고서 CLI가 구현됐다. PyTorch CPU 및 W&B offline 경로를 검사했다. 실제 Colab GPU·W&B online은 미검증이다. 아래 표·디렉터리·후보 수명주기는 구현 전 설계이며 실제 모듈 배치나 지원 CLI 목록이 아니다.

여기서 **대회 모델**은 제품 이미지의 불량 확률을 예측하는 비전 모델이다. 연구 하네스에서 조언하는 에이전트의 LLM 모델·effort와 구분한다. 후자의 배정은 레포 완성 후 별도로 구성한다.

## 1. 기본 코드베이스의 도입 범위

| 기반 | 가져올 책임 | 우리가 채울 것 | 설계 당시 상태 |
|---|---|---|---|
| CCDS | 원본/파생/모델/보고서 분리와 프로젝트 뼈대 | 대회 규칙·실행 계약·실제 패키지 | 폴더 역할만 참고; 템플릿 전체 미도입 |
| PyTorch·torchvision 등 모델 라이브러리 | 모델 구조·학습 연산·가중치 파일 읽기/쓰기 | 이미지 단위 출력·정확한 가중치 선택·학습/평가 공통 경로 | 후보 기반; 실제 설치 환경/모델 선정 전 |
| W&B SDK | Runs·Artifacts·Reports | 데이터/모델/평가/선택 ID와 복구 계약 연결 | 연결 전 |
| Colab notebook | 인증·경로·환경 확인·명령 진입점 | 재사용 가능한 핵심 로직은 공통 Python 코드에 배치 | 진입 notebook 미구현 |

CCDS는 완성된 이미지 대회 학습 코드가 아니다. 모델 라이브러리도 우리 검증·선택·보고서 규약을 대신 만들지 않는다. 기존 오픈소스 구현을 재사용할 때 코드·커밋·라이선스·실제 수정 부분을 기록한다. 모델/가중치는 첫 후보부터 공개일·사용 조건을 확인한다.

초기 제안은 CCDS의 역할 구분과 작은 Python 패키지다. Lightning-Hydra 전체 템플릿·DVC를 초기 필수 기반으로 확정하지 않는다. AMP·복구·callback의 중복이 실제 커지면 Lightning 같은 학습 기반을 도입할지 다시 판단한다. 설계 당시에는 trainer를 미정으로 두었다. v0.1은 공통 PyTorch 실행 경로를 사용한다.

## 2. 우리 코드베이스의 책임 경계

아래는 설계상의 구분이다. 모듈마다 별도 프레임워크나 플러그인 체계를 만들 필요는 없다. 첫 기준 모델의 공통 경로가 끝까지 작동하도록 구현 순서를 잡는다.

```text
src/defectlab/
  data/          원본 검증·이미지 카탈로그·split·dataset·공통 변환
  modeling/      모델 생성·head·출력 의미·가중치 로드 어댑터
  training/      학습·최적화·AMP·checkpoint·재개
  evaluation/    미학습 검증 예측·AUROC·비교·재현 검사
  inference/     이미지당 확률·제출 ID 순서·출력 형식
  ensemble/      구성원 버전·ID 정렬·확률 결합·recipe
  tracking/      W&B 및 로컬 결과/산출물의 얇은 연결
  reporting/     실제 결과의 표·그림·주장 근거 export
  management/    작업·자문·페어리뷰·결정·시간·세션 기록
```

- notebook마다 train loop를 복사하지 않는다. train 중 평가와 독립 validate/predict가 같은 모델·평가 변환·점수 변환을 사용한다.
- 모델을 바꿀 때 필요한 model factory/head 설정만 다르게 하고 데이터·검증·기록 계약은 유지한다. 구조가 다른데 억지로 하나의 거대한 추상 모델에 맞추지는 않는다.
- 데이터·관계 그룹·split은 학습 run이 임의로 바꾸지 않는다. 적용한 버전을 입력으로 받는다.
- W&B 연결이 없어도 제출 코드와 전달 가중치로 검증·추론할 수 있게 한다.
- 관리 하네스는 다음 작업과 근거를 연결하고, 실행기는 실제 학습·예측·파일 검사를 수행한다. 관리 상태만으로 실제 성공을 선언하지 않는다.

각 책임을 별도 명령으로 부를 수 있게 하되 첫 구현에서는 작은 함수·모듈로 충분한지 먼저 확인한다. 패키지 디렉터리 개수 자체를 완료 기준으로 삼지 않는다.

## 3. 대회 모델 관리의 대상

| 대상 | 의미 | 필수 식별·관계 |
|---|---|---|
| 모델 명세 | 구조·head·입력/출력 의미 | 생성 코드/라이브러리 버전·전처리·클래스 방향 |
| 사전학습 가중치 | 학습 시작에 사용할 허용된 외부 가중치 | 정확한 출처·공개일·사용 조건·파일 SHA-256 |
| 학습 설정 | 한 번의 학습을 정의하는 실제 설정 | 모델 명세·pretrained 버전·split·seed·최적화·precision |
| 학습 run | 실제 수행한 시도 | 실험 ID·코드/환경·설정·상태·비용 |
| 학습 checkpoint | 이어 학습할 상태 | model/optimizer·필요한 scheduler/scaler·epoch/step·난수/데이터 순서·run ID |
| 추론 가중치 | 평가·제출 추론에 사용할 모델 상태 | model spec·평가 변환·점수 변환·파일 hash·생성 run |
| 평가 결과 | 특정 가중치·프로토콜의 실제 점수와 예측 | weight 버전·data/split/protocol·전체 예측 ID/hash·AUROC |
| ensemble recipe | 구성원 점수를 이미지당 하나로 결합하는 방법 | 정확한 구성원 weight/평가 버전·전처리·가중치·집계 순서 |
| 최종 선택 기록 | 대회에 사용할 단일 모델 또는 ensemble | 선택 이유·비교 근거·정확한 버전/hash·재현 결과·CSV hash·실제 플랫폼 선택 기록 |

학습 run 하나가 checkpoint 여러 개를 만들 수 있고, checkpoint 하나를 다른 검증 프로토콜로 평가할 수 있다. 높은 지표 한 개를 모델 이름에 붙여 다른 split/프로토콜까지 확장하지 않는다. 구조가 같아도 가중치·전처리·학습 데이터가 다르면 같은 후보로 취급하지 않는다.

## 4. 모델 후보의 수명주기

```text
spec_draft → source_checked → training_started → trained
 → evaluated → candidate → selected → frozen_for_submission
                  ↘ rejected / deferred / failed / interrupted
```

이는 여러 증거를 연결하는 진행 보기다. 저장·평가·복구·선택을 단일 상태 값으로 뭉개지 않는다.

- `source_checked`: 실제 코드/가중치 출처·규정 근거를 기록했다. 모델이 좋다는 뜻은 아니다.
- `trained`: 학습 종료 상태다. 가중치 영속 저장·평가·복구는 별도로 확인한다.
- `evaluated`: 지정된 데이터/split/protocol에서 실제 평가했다. 완료된 결과와 선택에 쓴 결과를 구분한다.
- `candidate`: 선택할 이유와 비용을 설명할 수 있는 후보다. 성능 최대값만으로 자동 승격하지 않는다.
- `selected`: 비교 근거로 선택했다. 원래 baseline·다른 후보·실패를 지우지 않는다.
- `frozen_for_submission`: 정확한 버전과 recipe·출력·재현 증거를 고정했다. 대회에 실제 업로드/최종 선택됐다는 상태는 따로 기록한다.

검증에 사용한 모델과 전체 학습 데이터 재학습 모델은 별도다. 이전 검증 점수를 새 모델의 직접 측정값으로 복사하지 않는다. ensemble을 구성한 뒤 구성원 가중치가 바뀌면 새로운 recipe와 평가/선택 기록을 만든다.

## 5. W&B·Git·Drive의 분담

- **W&B Runs:** 실제 설정·loss·검증 AUROC·시간/메모리·실행 상태.
- **W&B Artifacts:** 가중치/필요한 checkpoint·설정·평가/recipe 파일의 버전과 생성/소비 관계.
- **W&B Reports:** 실제 비교 그래프·실패/한계·선정 설명을 모은 작업 문서.
- **Git:** 코드·작은 명세/평가 요약/선택 기록·원고. 현재 ignore에 막히지 않는 추적 위치를 구현 전에 정한다.
- **Drive:** 원본과 복구본·전달용 묶음. 실제 복사/업로드 완료와 해시·복구 확인을 기록한다.

`best`, `last`, `final`은 찾기 쉬운 alias/용도다. 최종 재현은 변경 가능한 별명만으로 하지 않고 정확한 Artifact 버전과 SHA-256을 고정한다. 예산·용량을 보며 필요한 best/last/최종 선택본을 보존하고 모든 epoch를 영구 업로드하지 않는다.

작은 모델/ensemble/선택 기록은 예를 들어 `management/models/`, `management/selections/` 같은 Git 추적 위치에 두는 안이다. `models/`의 바이너리 캐시와 구분한다. 실제 경로·스키마·ignore 검사는 구현 시 확정해야 하며 지금 만들어진 registry나 서버는 없다.

모델 Artifact를 저장·다시 읽을 수 있는 최소 흐름부터 시작한다. 조직용 model registry·배포 stage·serving 서버는 이 대회의 초기 요구가 아니다.

## 6. 코드·모델 관리에 대한 도메인 자문

- 코드/재현 관점: 공통 입력·평가 경로·의존성·테스트·실험 코드 변경의 의미를 검토한다.
- 모델링 관점: 구조/가중치·head/손실·학습 설정·입력 보존·비용을 검토한다.
- 평가 관점: 같은 후보 비교 조건·학습 제외 출처·선택 편향·모델/ensemble 근거를 검토한다.
- 운영 관점: 저장·다운로드·재개·자원·fallback을 검토한다.
- 페어리뷰: 중요한 모델/코드/평가 의미 변경에 별도 호출로 반례를 확인한다.

이 역할들에 사용할 에이전트 모델·effort는 레포 완성 후 구성한다. 현재 레포 구축 작업의 worker/reviewer/conductor 배분을 여기에 적용하지 않는다.

## 7. 구축 순서와 통과 조건

1. 가설·EDA·split·평가 대상·이미지당 출력 의미를 먼저 정한다.
2. 실제 기반 버전·환경과 작은 모델 어댑터의 입출력 계약을 정한다.
3. 단일 모델의 train→checkpoint→validate→predict→reload 경로를 구현한다.
4. 고정 이미지·ID 순서·양성 방향·수치·epoch 재개·W&B 없는 추론을 검사한다.
5. 모델/평가/선택 기록에서 가중치·코드·환경·전처리·split·예측을 역추적한다.
6. 같은 입력 계약의 두 번째 모델을 연결한 뒤 작은 튜닝·ensemble을 붙인다.
7. 선택 버전을 새 환경에서 다시 읽어 검증·제출 CSV와 보고서 근거를 확인한다.

이 문서는 구축 범위의 설계 근거다. 구현된 시작 모델·설정·실행 계약과 검사 한계는 RUNBOOK 및 CURRENT-STATUS에서 확인한다.
