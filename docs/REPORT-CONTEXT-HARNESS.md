# 보고서 작성 문맥 관리 하네스 설계

2026-11-17 운영 기준: [운영 진입점](OPERATIONS.md) → [현재 상태](CURRENT-STATUS.md)에서 시작한다. 아래 본문은 구현 전 설계 의도·완료 조건의 이력이며 당시 상태나 제안 명령은 현재 실행 지시가 아니다. 실제 CLI는 [실행 가이드](RUNBOOK.md)와 소스·테스트를 따른다.

현재: results/context/freshness/freeze는 실제 결과표·근거 묶음·파일 변경/누락 검사·스냅샷을 지원한다. 원고 생성·자동 인용·의미 기반 변경 감지는 지원하지 않는다. 실제 대회 실험 결과·최종 원고는 없다. 아래는 보고서 관리의 설계 계약이다.

## 1. 관리 대상

수업 제출용 기술보고서의 각 주장이 어떤 연구 질문·관측·실험·선택에 근거하는지 추적한다. 작성자가 필요한 절의 근거를 읽고, 검토자가 같은 버전과 근거를 다시 확인할 수 있게 한다.

W&B Reports는 실제 run 비교와 연구 분석을 모으는 작업 문서, Git의 원고는 제출 본문·참고문헌·재현 부록의 관리 대상이다. 제출 시점에는 두 문서가 참고한 실험 집합과 버전을 고정한다. 그래프가 나중 run을 자동 포함한다고 기존 제출본의 결과까지 바뀐 것으로 처리하지 않는다.

## 2. 공통 문맥과 절별 문맥

| 문맥 | 필요한 내용 | 실제 근거 |
|---|---|---|
| 보고서 전체 | 과제·평가·제약·독자·형식·용어·핵심 질문·현재 결론 범위 | 대회 규정·수업 공지·용어·확정한 연구 계획 |
| Introduction | 왜 이 문제와 질문을 다루는가 | 과제 정의·직접 확인한 배경·실제 연구 범위 |
| Related Work | 어떤 대안이 있고 왜 후보를 골랐는가 | 직접 확인한 원문/코드·출처 카드·적용 한계 |
| Methods | 실제 사용한 모델·전처리·split·학습·추론·ensemble | 코드·resolved config·가중치·데이터/분할·실제 실행 기록 |
| Results | 무엇을 같은 조건에서 비교했고 무엇을 측정했는가 | 고정한 run 집합·예측·평가 protocol·실패 상태·표/그림 |
| Discussion | 가설을 어디까지 지지하고 무엇을 모르는가 | 비교 결과·반례·오류 사례·불확실성·선택 편향·자원 제약 |
| Abstract/Conclusion | 최종적으로 근거가 지지하는 핵심 주장 | 최종 선택·고정된 결과·주장 목록·한계 |
| References/재현 부록 | 출처와 다시 실행하는 방법 | 확인한 인용 정보·라이선스·환경·명령·실제 재현 결과 |

계획 중인 Methods와 실제 수행한 Methods는 표시를 구분한다. 제안했던 모든 후보를 실제 실행했다고 쓰지 않는다. 최종 결과가 없더라도 배경·질문·확인된 데이터 설명은 먼저 작성할 수 있다.

## 3. 작성 요청에 줄 최소 문맥 묶음

1. 절의 목적, 답할 질문, 독자·제출 형식, 포함/제외 범위, 작성 대상 버전.
2. 필요한 공통 사실·용어와 그 근거 위치.
3. 해당 절의 claim ID, 근거, 반례·미해결 쟁점.
4. 해당되는 source card와 원문 위치, experiment/run·config·split·평가·가중치의 고정 식별자.
5. 표·그림의 값/생성 입력/정의와 sample ID·선택 기준. 해석에 필요할 때만 제한된 사례를 제공한다.
6. 직전 원고·검토 지적·처분·그 절과 앞뒤 절의 연결 요약.
7. 작성 결과가 무엇을 주장하면 안 되는지: 미측정 값·미확인 인용·인과 설명·적응 범위 등 현재 근거의 한계.

전체 대화·모든 run 로그·전체 원본 이미지·가중치 바이너리를 매번 문맥에 넣지 않는다. 원본은 기존 위치에 두고 ID·경로·hash와 필요한 근거만 연결한다. 문맥 한도가 부족하면 절/질문을 나누거나 명시적으로 범위를 줄이며 조용히 뒷부분을 버리지 않는다.

문맥 묶음을 만들었다고 작성·검토가 실행된 것은 아니다. 실제 요청·응답·대상/출력 hash·한계는 공통 하네스 기록 규약으로 연결한다. 이 보고서 역할의 에이전트 모델·effort는 레포 완성 후 별도 구성한다.

## 4. 주장과 근거의 장부

기존 연구/실험 카드를 재작성하지 않고 보고서의 주장만 연결한다. 최소 필드는 다음과 같다.

- `claim_id`, 주장 초안, 연결 section ID와 원고 위치.
- 구분: 외부 원문 주장 / 우리 관측 / 해석 / 가설 / 향후 계획.
- hypothesis/question ID와 source/experiment/run·data/split/protocol·weight/ensemble 버전.
- 표·그림 ID, 생성 입력·코드·정밀도/집계 정의, 사례 sample ID·선택 기준.
- 주장에 반하는 결과·불확실성·선택 과정의 한계.
- 상태: draft / evidence_linked / needs_evidence / needs_update / reviewed / frozen.
- 해당 주장·근거 버전을 검토한 기록과 지적 처분.

상태는 그 버전의 기록 상태다. evidence_linked는 참이라는 증명이 아니고, reviewed도 관측의 범위를 넘어선 과학적 정당성을 자동 보장하지 않는다. 검토 후 바뀌면 변경 상태를 남긴다.

수치는 생성된 표/평가 결과를 기준으로 삼는다. 스무딩된 그래프나 화면에 반올림된 값에서 정확한 AUROC를 다시 읽지 않는다. 다른 split/프로토콜의 수치를 같은 비교처럼 합치지 않는다. 수행하지 않은 Private 평가·통계 검정·재현은 채우지 않는다.

## 5. 작성·검토·처분

```text
절별 brief와 고정 근거 → 작성 → 별도 페어리뷰
 → 지적 처분·원고 수정 → 변경 범위 표시 → 제출 스냅샷
```

- 작성자는 읽은 근거 범위에서 문장을 구성한다. 근거가 없으면 단정하지 않고 needs_evidence로 남긴다.
- 데이터/모델/평가/운영 자문은 해당 절의 기술적 의문에만 붙인다. 모든 문단에 모든 역할을 호출하지 않는다.
- 별도 페어리뷰는 주장-수치-근거 일치, 비교 공정성, 인용 정확성, 실패·한계 누락, 원고와 구현/최종 선택의 정합성을 본다.
- 기본은 한 차수 검토와 처분이다. 단순 문장 교정은 전체 과학 검토를 다시 요구하지 않는다.
- 평가 의미·핵심 결론·근거 run이 바뀌면 영향을 받은 주장·절만 새 버전으로 확인한다.
- 기존 원고와 사용자의 직접 수정·설명은 보존한다. 새 초안이 이전 기록을 조용히 대체하지 않는다.

원문이 없는 인용을 만들지 않는다. 원문 주장과 우리 데이터에서 입증한 결과를 섞지 않으며, 문장 해석을 외부 원문의 사실로 돌리지 않는다.

## 6. 변경 영향과 문맥의 유효성

| 바뀐 것 | 다시 확인할 주장·절 |
|---|---|
| 데이터/카탈로그/제외 목록 | 데이터 설명·분할·관련 실험 수치·한계 |
| split·그룹·fitting scope·평가 protocol | Methods·관련 Results·Discussion·핵심 결론 |
| 모델·전처리·학습 설정 | Methods·해당 비교·재현 부록 |
| 선택한 checkpoint·ensemble recipe | 최종 비교·Abstract/Conclusion·재현·제출 기록 |
| 표/그림 생성 입력·집계 방식 | 해당 표/그림과 그것을 인용하는 문장 |
| 외부 source의 확인 상태·버전 | 해당 인용·Related Work·선정 근거 |

hash/버전 변경은 영향 후보를 찾는 신호다. 무엇이 의미상 바뀌었는지는 작성자/검토자가 판단한다. 시스템이 임의로 연구 결론을 다시 쓰지 않는다. 갱신이 필요한 상태를 남기고 실제 근거로 변경을 처리한다.

제출본은 특정 보고서 버전·원고·claim 목록·run 집합·표/그림·참고문헌·선택 모델·재현 부록을 함께 고정한다. 이후 Private 결과나 추가 실험은 수정/추가 이력으로 남기고, 선택 당시 이미 알고 있던 근거처럼 과거 설명을 바꾸지 않는다.

## 7. 최소 파일 역할 제안

```text
reports/
  WRITING-PLAN.md       절별 질문·작성 시점
  context/              outline/공통 사실/주장 목록/절별 brief의 작은 기록
  drafts/               원고·작성자 수정·검토 이력
  tables/ figures/       실제 결과에서 생성한 산출물
  snapshots/            제출 시점의 고정 목록·원고·결과 식별
```

기존 research/experiments/management의 사실·실행 기록은 재사용한다. 같은 출처/실험을 보고서 디렉터리에 별도 진실로 복제하지 않는다. 이 경로들은 제안이며 새 데이터베이스·문서 서비스·자동 작성기는 구현하지 않았다.

## 8. 향후 구현의 완료 기준

- 대표 주장 하나가 원고→표/그림→예측/평가→가중치/config/code→split/data로 연결된다.
- 절 작성 시 필요한 근거와 마지막 검토/처분을 재구성할 수 있고, 없는 자료는 명시된다.
- 근거 run이나 split 변경 시 관련 절을 needs_update로 표시하고 과거 reviewed를 최신본에 승계하지 않는다.
- 미측정 값·미확인 인용·다른 protocol 혼합이 확인되면 그 주장의 채택을 막고 다른 작성 작업은 계속한다.
- 제출 스냅샷에서 표·그림·원고·최종 선택·재현 결과의 버전이 맞는다.
- 실제 작성/검토 호출과 문맥 준비 상태를 구분한다.
