# 대회 연구·실험·보고서 구체 기획 v0.2

2026-11-18 현재 질문·기법·실행 우선순위는 [연구 계획v1](research/RESEARCH-PLAN-2026-11-18.md)에 고정했다. 아래 v0.2는 범위·설계 이력으로 보존한다. 후속 계획은 실제 수행 완료나 최종 모델 선택을 뜻하지 않는다.

기준일: 2026-11-17. 사용자의 후속 구현 지시로 가벼운 v0.1 실행기를 구축했다. 작업 시작은 [운영 진입점](OPERATIONS.md)과 [현재 상태](CURRENT-STATUS.md)를 따른다. 아래는 연구 범위와 설계 근거이며 실제 명령·설치·검사 범위는 [실행 가이드](RUNBOOK.md)를 따른다. 대회 GPU 학습·최종 모델 성능은 아직 측정하지 않았다.

## 1. 목표와 성공 조건

최종 선택한 모델 또는 앙상블에 대해 다른 컴퓨터의 새 환경에서 다음을 수행할 수 있어야 한다.

1. 지정된 데이터와 분할을 검증한다.
2. 지정된 가중치로 검증 예측을 다시 만들고 AUROC를 재계산한다.
3. 테스트 이미지 800장의 불량 확률을 제출 양식 순서로 생성한다.
4. 보고서의 각 핵심 결과를 실험 ID, 설정, 코드 커밋, 가중치 버전, 검증 예측으로 추적한다.
5. 학습 코드와 환경도 제공하여 학습부터 추론까지의 과정을 확인할 수 있게 한다.

대회 모델의 성능과 실험 과정·설명·재현성을 함께 준비한다. 높은 Public 점수만으로 모델을 결정하지 않는다.

## 4. 데이터와 검증 설계

관측값: 학습 이미지 10,821장, 불량 1,200장. 학습은 약 150만 픽셀의 직사각형 8종 크기, 테스트는 정사각형 4종 크기다. 이는 JPEG 헤더 조사 당시의 관측이다. 후속 전수 픽셀 디코드는 완료했으며 제품 유형·촬영 관계·근접 중복은 미확인이다. 세부 범위는 [검증 기록](IMPLEMENTATION-VALIDATION.md)을 따른다.

- 최초 탐색: 제공 학습 이미지에서 제품 종류, 결함 크기, 여러 제품 배치, 해상도와 클래스의 관계를 살핀다. 테스트 정답·외부 원본 데이터·공개 라벨은 조회하지 않는다.
- 정확한 중복은 SHA-256으로 찾는다. 촬영 개체·연속 촬영·근접 중복이 있으면 근거를 적고 그룹으로 묶는다. 파일명이나 해상도만으로 제품 그룹을 확정하지 않는다.
- 제안: 클래스 비율을 고려한 단일 고정 holdout부터 시작한다. 종속 표본이 있으면 그룹 분리를 우선한다. 분할 비율은 클래스 수·그룹 조사 후 확정하며 약 80/20은 후보일 뿐이다.
- 동일 실험 비교에는 같은 split 해시와 검증 프로토콜을 사용한다. 분할 변경 결과를 같은 표에서 단순 순위로 섞지 않는다.
- 검증·테스트 전처리는 결정론적으로 고정한다. 전처리 통계를 추정한다면 학습 부분만 사용한다.
- 첫 모델은 전체 이미지 분류를 기준선으로 제안한다. 작은 결함을 보존하는 입력 크기와 비율 보존 방법을 비교한다. 무조건 224로 줄이거나 크롭해도 된다고 확정하지 않는다.
- 크롭/패치는 별도 가설이다. 불량 부분이 사라진 패치에 불량 라벨이 붙는 문제, 여러 제품 배치, 패치 점수의 이미지 단위 집계 방법을 검증해야 한다.

## 5. 실험 한 건의 계약

실험 계획과 실제 실행을 구분한다. 같은 계획을 다른 시드로 실행하면 별도 run을 만든다.

계획에 필수인 값:

- `experiment_id`, 질문, 가설, 근거 `source_ids`, 비교 기준 실험.
- 바꾸는 변수, 고정할 변수, 설정 파일, split 해시, 주지표와 보조 관측값.
- 최대 후보 수·실행 예산, 중단 조건, 결과를 판단할 규칙.

실행 결과에 필수인 값:

- `run_id`, experiment ID, Git commit와 코드 변경 여부, 실제 사용 설정과 해시.
- 데이터 manifest와 split의 해시, 시드, OS/Python/패키지 버전, GPU 모델·VRAM.
- 상태: planned / running / completed / failed / oom / interrupted.
- 검증 AUROC, loss, 학습·검증 시간, 최대 GPU 메모리, epoch 수.
- W&B run URL, 정확한 가중치 Artifact 버전과 파일 SHA-256.
- 검증 예측·테스트 예측 파일 해시와 저장 위치. 측정하지 않은 값은 null이다.
- 해석과 한계. 실패는 없애거나 성공 run으로 다시 쓰지 않는다.

AUROC는 전체 검증 예측을 모아 계산하며 배치별 AUROC를 단순 평균하지 않는다. Public Score는 별도 항목에 수동 기록하고, Private Score는 실제 결과 공개 전 채우지 않는다.

## 6. 무료 Colab 실험 예산과 튜닝

먼저 시스템 실험 P000을 한다. 할당 GPU·메모리·디스크를 확인하고 데이터를 ZIP으로 VM 로컬에 복사·해제한 뒤 데이터 검증을 통과시킨다. 사용할 backbone·입력 크기·배치로 실제 학습+검증 epoch를 측정한다. 최초 준비 시간과 정상 상태 epoch 시간을 분리한다.

예상 시간 = 데이터 준비·초기화 + 측정 epoch 시간 × 목표 epoch 수 + 추론·저장·검증 여유. GPU 종류가 바뀌면 다시 측정한다. 무료 GPU 가용 시간을 임의의 고정 시간으로 계산하지 않는다.

튜닝 제안:

1. 처음에는 한 고정 split, 한 seed, 기준 모델 한 개로 시작한다.
2. 한 질문에 후보 2~3개를 먼저 계획한다. 이는 초기 운영 제안이며 계산 예산 측정 뒤 확정한다.
3. 학습률, 입력 크기, 증강, 손실 등의 비교를 순차 진행한다. 모든 조합의 곱을 자동 실행하지 않는다.
4. epoch 예산과 조기 종료 규칙을 후보 간 맞추고, 성능·시간·메모리를 함께 비교한다.
5. 유망한 소수만 다른 seed 또는 사전에 정한 추가 검증으로 확인한다. 최초부터 전 모델의 다중 fold 학습을 의무화하지 않는다.
6. 작은 튜닝을 시작하기 전에 최종 확인 방법과 선택 횟수 기록 방식을 정한다. 추가 seed는 최적화 변동을 확인하지만 같은 holdout의 선택 편향을 제거하지 않는다. 별도 확인 예산이 없으면 그 한계와 모든 선택 횟수를 남긴다. 같은 검증 ID의 차이는 paired 비교하고 종속 그룹이 있으면 그 단위의 불확실성을 고려한다.

## 7. 앙상블 계약

첫 구현은 확률 단순 평균과 비음수 가중 평균이다. 모델 두 개부터 시작하고 개선 근거가 있을 때만 늘린다. rank 평균·stacking은 초기 범위 밖이다.

- 각 구성원의 검증 예측은 해당 이미지로 학습하지 않은 모델에서 나온 것이어야 한다.
- 첫 방식은 같은 고정 holdout의 예측을 결합한다. cross-validation을 도입할 때는 행별 OOF 출처를 검증해야 한다.
- 결합 전 이미지 ID 중복·누락·라벨·split 해시를 검사하고 ID 기준으로 정렬한다. 행 순서만 믿고 배열을 더하지 않는다.
- 가중치는 검증 데이터만으로 정하고, 테스트 예측을 보기 전에 조합을 고정한다. 가중치는 0 이상이며 합이 1이어야 한다.
- 합친 검증 확률에서 AUROC를 다시 계산한다. 개별 모델 AUROC 평균은 앙상블 성능이 아니다.
- 조합 파일에는 구성원 Artifact의 정확한 버전, 예측 해시, 가중치, 전처리·확률 변환과 view/fold/model 집계 순서, 가중치 선택 횟수를 기록한다. OOF에서 최종 테스트 추론으로 갈 때 구성원·fold 집계·전체 재학습 관계를 명시한다.
- 최종 테스트 예측에도 같은 집계 방법과 가중치를 적용한다. 공개 점수에 맞춰 조합을 무제한 변경하지 않는다.
- 개선이 불확실하거나 재현·시간 부담이 크면 단일 모델을 최종 선택할 수 있다.

## 8. W&B와 파일 저장

W&B Runs는 실험·지표, Artifacts는 선택 모델과 재현 자료의 버전, Reports는 비교 그래프와 연구 분석을 맡긴다. 필수 결과를 Git/Drive에서도 확인할 수 있도록 compact 결과 JSON·표·모델 복구본을 보존한다.

- W&B 프로젝트의 실제 비공개 접근 범위를 확인한 뒤 연결한다. entity와 project는 아직 미정이다.
- `best`는 검증 기준 선택 모델, `last`는 학습 재개용, `final`은 제출 선택 기록으로 사용한다. 최종 기록은 변경 가능한 alias만 남기지 않고 정확한 버전과 SHA-256을 고정한다.
- 학습 재개용 저장에는 model/optimizer/scheduler(사용 시)/AMP scaler(사용 시)/epoch/난수 상태/설정/run ID가 필요하다. W&B run 재개와 학습 상태 복구는 별개다.
- every-epoch 가중치를 전부 장기 업로드하지 않는다. 저장 용량과 업로드 비용을 확인하고 best/last 및 실제 최종 선택본 중심으로 보존한다.
- 원본 이미지는 Drive에 보존한다. 데이터 파일 목록과 분할 파일·해시로 실험 입력을 식별하며 원본 전체를 W&B에 중복 업로드할 필요는 없다.
- API key는 Colab Secrets 또는 로컬 환경 변수로 공급한다. Git과 노트북 출력에 넣지 않는다. 데이터·예측·코드의 자동 업로드 범위를 명시적으로 설정한다.
- 제공 규칙상 금지된 것은 원격 모델의 예측 결과 사용이다. 지표·가중치 저장은 기능상 다르며, 주최 측의 별도 승인을 받은 것으로 기록하지 않는다.

## 9. 재현은 세 수준으로 검사

| 수준 | 검사 | 통과 기준 |
|---|---|---|
| 파일 무결성 | 데이터·가중치·설정·분할·제출 선택 기록 | 기록된 SHA-256과 정확히 일치 |
| 고정 가중치 평가·추론 | 새 세션에서 검증 AUROC·행별 예측·제출 CSV 생성 | 컬럼·행·순서·유한값·0~1 범위, 사전 고정한 수치 허용오차 통과 |
| 학습 과정 재실행 | 설정·코드·환경으로 학습 후 비교 | 절차와 차이를 기록; 다른 GPU/버전에서 동일 비트 결과를 보장한다고 주장하지 않음 |

P000에서는 수치 차이를 측정하는 방법과 허용오차 정책을 정한다. 최종 예정 추론 경로의 같은 가중치 반복 평가로 기준을 확인하고 최종 모델 선택 전에 수치를 고정한다. 통과시키기 위해 사후에 넓히지 않는다. 제출 CSV에는 예시 파일과 동일한 이미지 목록·순서를 사용한다. 선택한 ensemble도 구성원 로딩부터 조합까지 새 세션에서 재실행한다.

최종 선택 모델은 검증에 쓴 모델인지 전체 학습 데이터로 재학습한 별도 모델인지 구분한다. 전체 데이터 재학습 모델에 이전 holdout 모델의 검증 점수를 그대로 붙이지 않는다. 검증용 모델과 최종 제출 모델의 관계·선정 근거를 보고서에 명시한다.

## 10. 과거 제안 인터페이스 — 현재 CLI와 다름

아래는 구현 전 제안의 이력이며 실행 지시가 아니다. 현재 명령은 `defectlab --help`와 RUNBOOK을 따른다. 예를 들어 verify-data/prepare-split/validate/build-report 대신 실제 명령은 verify/split/evaluate/results이며 자동 원고 생성은 지원하지 않는다.

```text
verify-data      원본 데이터 파일 검증 (설계 당시 verify_data.py만 구현됨)
prepare-split    학습·검증 목록 생성과 누수 검사
train           계획·설정으로 학습하고 W&B/체크포인트 기록
validate        고정 가중치 검증 예측과 AUROC 생성
predict         제출 양식에 맞춘 테스트 확률 생성
ensemble        정렬·검사한 예측 파일 결합
reproduce       선택 manifest로 검증·제출 재현과 비교
build-report    실제 결과에서 비교표·그림·재현 부록 생성
```

튜닝은 동일 train 명령을 설정 후보별로 순차 호출한다. 초기에는 별도 튜닝 서버가 없다. Colab 노트북은 진입점·인증·경로 지정 역할이고, 핵심 학습 로직은 공통 Python 코드에 둔다.

## 11. 구현 순서와 판단 시점

각 단계의 완료/진행 표시는 task·decision·증거의 적용 버전에 근거한 루트 판정이다. 선행 근거 변경 시 진행자가 영향받는 후속 단계까지 `needs_reassessment`로 표시하고 새 기준에서 완료 조건·추가 작업·담당을 재판정한다. 과거 실행 결과는 보존하고 영향받지 않는 작업은 계속한다. [루트 재판정 절차](MANAGEMENT-HARNESS.md#51-루트-단계의-근거와-변경-시-재판정)와 [단계 판정 기록](harness/RECORDS.md#루트-단계-판정)을 따른다.

| 단계 | 산출물 | 다음으로 갈 조건 |
|---|---|---|
| A. 질문·가설 | 규정·관측/가정·반증 예측·EDA 질문 | 무엇을 관측하고 어떤 비교를 할지 설명 |
| A2. 데이터·검증 설계 | 원본 검사·EDA·카탈로그·관계 근거·분할·전처리 | 질문별 관측/미확인과 첫 모델 결정 연결 |
| B. 단일 모델 수직 구현 | train→validate→predict→가중치 저장→재현 | 합성 데이터 기능검사 및 실제 Colab P000 결과 |
| C. 기준 실험 | 고정 분할의 baseline run·보고서 초안 | 오류 분석과 시간·메모리 예산 확인 |
| D. 집중 비교 | 연구 카드와 작은 튜닝 결과 | 유망한 소수 모델 선정과 추가 확인 |
| E. 앙상블·최종 선택 | 단일/앙상블 비교·고정 manifest | 성능·시간·재현성으로 최종 선택 |
| F. 제출 리허설 | 새 세션 재현 결과·제출 코드 묶음 | 검증·추론·출력·파일 해시 검사 통과 |
| G. 보고서 완성 | 결과 해석·실패 분석·참고문헌·재현 부록 | 표와 주장을 실제 결과에 대조 |

학습 자동화보다 단일 모델의 끝까지 이어지는 실행 경로를 먼저 검증한다. 자동화는 실제로 필요한 반복부터 늘린다. GPU 결제나 대회 제출은 자동으로 실행하지 않는다.
