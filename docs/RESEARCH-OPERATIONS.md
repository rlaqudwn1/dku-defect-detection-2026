# 연구 시간·무료 Colab 운영 설계

2026-11-17 운영 기준: [운영 진입점](OPERATIONS.md) → [현재 상태](CURRENT-STATUS.md)에서 시작한다. 아래 본문은 구현 전 설계 의도·완료 조건의 이력이며 당시 상태나 제안 명령은 현재 실행 지시가 아니다. 실제 CLI는 [실행 가이드](RUNBOOK.md)와 소스·테스트를 따른다.

현재: 로컬 장부는 명시 관측 구간의 합집합·예약 소비·저장 영수증을 지원한다. 실제 대회 GPU 사용 시간은 미측정이다. 자동 접속·모니터링·종료·스케줄러는 없다. 아래는 운영 설계와 관측 기준이다.

## 1. 시간을 세 종류로 분리

| 시간 | 의미·출처 | 합산 원칙 |
|---|---|---|
| 사람 연구 작업 | 사용자가 시작/중지하거나 작업 구간을 확인한 기록 | 같은 사람의 겹친 구간은 한 번만 계산. 단순 세션 경과를 집중 작업 시간이라고 부르지 않음 |
| GPU 자원 관측 | notebook/telemetry 또는 사용자가 실제 확인한 할당·실행 구간 | 같은 GPU resource의 중복 구간은 합집합, 여러 resource는 자원 시간으로 합산 |
| 학습·검증·추론 소요 | 실제 실행기가 측정한 단계 시간 | GPU 세션의 하위 관측과 구분. 총 연구 시간에 다시 더하지 않음 |

관측 구간·수집 시각·source·task/run·resource ID를 남긴다. 수동 입력은 수동 관측이라고 표시한다. 로컬 CLI가 닫혔다고 Colab도 종료된 것으로 취급하지 않는다.

## 2. 예산과 예약

연구자가 정한 한도는 Colab이 보장하는 quota가 아니다. 무료 Colab의 실제 남은 GPU 시간·제공 잔량·과금 단위를 보지 못했다면 unknown이다.

- planned: 현재 계획의 총 추정량. P000 등 어떤 측정에 근거했는지와 불확실성을 포함한다.
- reserved_remaining: 시작 전/실행 중 작업에 앞으로 필요한 예상량.
- actual: 실제 관측한 사용량. 실패·OOM·중단 비용도 포함한다.
- actual이 늘면 같은 작업의 예약을 소비한다. 완료/취소 시 잔여 예약을 해제한다.
- 같은 단위에서 `actual + reserved_remaining`을 연구자 한도와 비교한다. 사람 시간·GPU 시간·저장량을 합치지 않는다.
- 최종 재현·추론·다운로드·복구의 몫을 탐색과 구분해 남긴다. 모르면 숫자를 임의로 채우지 않고 먼저 측정한다.

후보별 설정·GPU가 다르면 기존 epoch 측정치를 무조건 재사용하지 않는다. 같은 학습 기회와 같은 자원 예산 비교를 구분하고 실제 계산량을 보고한다. 추정 상한을 넘는다고 새 결제나 다른 계정 우회로 진행하지 않는다.

## 3. Colab 세션 상태

```text
unknown → observed_running → observed_closed
                    ↘ stale / end_unknown → 재관측 또는 종료 확인
```

- 시작: 실제 GPU·환경·task/run·체크포인트·관측 방법을 기록한다.
- 관측: 마지막 관측 시각과 확인된 구간만 갱신한다. notebook이 만든 JSON을 수동 수집하는 경로도 가능한 안이다.
- stale/end_unknown: 마지막 관측 이후를 계속 실행 또는 종료로 자동 판정하지 않는다. 확인된 시간과 미확인 꼬리 구간을 분리한다.
- 종료: 사용자가 확인한 종료 방법·시각 또는 실제 telemetry를 기록한다.
- 재연결: 같은 세션인지 새 세션인지 resource와 실제 상태로 확인한다. GPU 변경은 새 성능 측정의 이유다.

하네스가 상주 heartbeat나 브라우저 자동화를 이미 제공하는 것으로 설명하지 않는다. 처음에는 수동 관측과 저장 영수증만으로도 시작할 수 있다.

## 4. 실행 완료와 복구 가능을 분리

저장·복구의 관측 상태 제안:

```text
로컬 저장 시도 → 로컬 파일 확인 → 원격 복사/업로드 요청
 → 목적지 완료·해시 확인 → 새 세션 다운로드·해시 확인
 → 가중치 평가/학습 재개 시험
```

- 로컬에서는 임시 파일 저장 후 무결성 확인·이름 교체로 반쪽 checkpoint를 피하는 구현을 검토한다.
- Drive 복사나 W&B 업로드를 요청한 것만으로 `durable`이라고 표시하지 않는다.
- 파일의 목적지·해시·완료 시각·확인 방법·관련 run/epoch와 증거를 남긴다.
- W&B run 재개, checkpoint 다운로드, 실제 학습 상태 복원은 별도 확인이다.
- 통신 실패 시 미동기화 상태·로컬 결과를 보존하고 다음 세션에서 중복 기록 없이 이어갈 방법을 정한다.
- 한 epoch가 세션에 비해 너무 길 때만 중간 저장의 복잡도를 추가한다.

실제 저장 quota·인증·다운로드 권한은 연결 시 확인한다. 원격 저장 성공이나 새로운 세션의 복구 성공은 아직 실측하지 않았다.

## 5. 운영 자문이 답할 질문

1. 마지막으로 확인한 상태와 아직 모르는 상태는 무엇인가?
2. 다음 후보의 준비·학습·검증·추론·저장·복구를 포함한 비용 범위는?
3. 같은 자원에서 더 작게 검증할 수 있는 방법은?
4. 남겨 둘 재현·최종 추론 몫을 잠식하는가?
5. 지금 종료돼도 어느 영속 버전에서 재개할 수 있는가?
6. 마감 전에 새 학습 없이 사용할 fallback이 있는가?

자문 결과는 다음 작업 순서·비용 추정·중단 기준·필요한 관측으로 남긴다. 관측되지 않은 비용·계산 단위를 만들지 않는다.

## 6. 달력과 마감

사용자 작업 시간대는 Asia/Seoul이다. 대회 공지의 기준 시간대는 공식 페이지와 제출 안내를 확보할 때 함께 기록한다.

- 대회 종료: 제공 공지 기준 2026-11-30 10:00.
- 코드 제출: 2026-11-30 10:00 ~ 2026-12-01 10:00.
- 보고서: 기존 수업 공지 기준 2026-12-08 23:59.

첫 baseline 직후 작은 재현 리허설을 수행하는 안이다. 제안상 11월 27일까지 fallback과 첫 완전 리허설을 확보하고, 이후는 최종 선택·복구·재현을 우선한다. 이는 교수의 추가 요구가 아니라 무료 자원 변동에 대비한 운영 목표다. 탐색 중단 목표와 공식 제출 기한을 별도 기록한다.

## 7. 향후 구현을 검사할 시나리오

- 같은 관측을 두 번 수집해도 actual이 두 번 증가하지 않는다.
- 사람 작업과 GPU 실행이 겹쳐도 서로 합산하지 않는다.
- 관측이 끊긴 세션은 end_unknown이고 임의의 종료·사용 시간을 생성하지 않는다.
- 예약을 소비한 actual과 남은 예약을 중복 계산하지 않는다.
- 파일 영속 저장·새 세션 복구가 확인되지 않으면 해당 상태를 완료로 올리지 않는다.
- 상태 저장 도중 중단돼도 직전 확정 기록과 정정 이력이 보존된다.

위 시나리오의 로컬 장부 검사는 구현·테스트됐다. 실제 원격 저장·Colab 관측과 복구 성공은 별도 증거가 필요하며 미검증이다.
