# 연구 관리 메타 하네스 설계 v0.2

상태: 설계 제안. 이 문서의 역할 호출·장부·명령은 구현되거나 자동 실행되는 기능이 아니다. 현재 실행 가능한 코드는 기존 파일 무결성·텍스트 검사 도구다. 앞서 작성했던 관리 스크립트 초안은 실행 경로에서 분리했으며 커밋하지 않았다.

## 1. 관리 대상과 경계

사용자가 요구한 것은 각 도메인의 전문가 조언, 독립적인 페어리뷰 연구원, 연구 시간·무료 Colab 운영을 포함한 대회 연구 관리다. 하네스는 이 관계를 잇는 공통 관리 계층으로 설계한다.

- 공통: 작업·근거·가설·실행·검토·결정·시간·복구 기록의 식별과 연결.
- 도메인별: 무엇을 입력받아 어떤 질문을 검토하고 어떤 산출물을 낼지 정의.
- 진행자: 현재 주 작업 에이전트. 다음 작업을 정하고 실제 요청·검토 결과를 보존한다.
- 실행기: 이후 구현할 데이터·학습·평가·추론 명령. 관리 장부를 기록하는 것과 실제 실행을 분리한다.
- 외부 도구: Colab은 직접 학습·추론, W&B는 Runs/Artifacts/Reports, Drive는 원본·복구본, Git은 코드·설계·작은 기록.

도메인마다 서버나 상주 에이전트를 만드는 방식은 초기 범위에 넣지 않는다. 실제 호출 수는 필요한 관점에 맞춘다. 운영과 검토는 실험 실행기 위의 공통 관리 층이며, W&B의 모델 지표를 다시 구현하지 않는다.

## 2. 도메인별 책임과 역할

| 도메인 | 자문 역할 | 핵심 질문 | 입력 | 출력·다음 연결 |
|---|---|---|---|---|
| 연구 설계 | 연구 방법론 연구원 | 어떤 관측이면 설명을 지지·약화하는가? 다음 작은 비교가 무엇인가? | 규정, 연구 질문, 근거 카드, EDA, 이전 결과 | 가설·반증 조건·대안·비교 계획 → 데이터/평가/모델 |
| 데이터 | 데이터·시각 분석 연구원 | 어떤 이미지·라벨·촬영 관계가 있으며 전처리가 무엇을 잃는가? | 원본 manifest, 카탈로그, 표본 ID, 조사 기록 | EDA 해석·관계 후보·입력 보존 판단 → 평가/모델 |
| 코드·재현 | 연구 소프트웨어·재현 연구원 | 공통 코드·입출력·환경·변경이 실험 의미를 유지하는가? | 코드/설정 설계·의존성·기능 검사·재현 묶음 | 코드 경계·검사·이식성 권고 → 구현/재현 |
| 모델링 | 컴퓨터 비전·최적화 연구원 | 이 모델·가중치·전처리·손실을 선택할 근거와 비용은? | 가설, 데이터 관측, 가중치 규정 근거, 분할·예산 | 작은 기준 모델·학습 설정·대안·예상 실패 → 실행/운영 |
| 평가 | 검증·통계 연구원 | 어떤 일반화를 추정하며 선택 편향과 누수는 어디에 있는가? | split·그룹 근거, fitting 범위, 예측·선택 이력 | 평가 프로토콜·확인 계획·결론 한계 → 실험/선택 |
| 연구 운영 | 시간·Colab 운영 연구원 | 지금 자원으로 무엇을 먼저 하고 어디서 복구할 수 있는가? | 관측 시간·GPU·세션·저장 영수증·마감·후보 비용 | 다음 작업 순서·예산 제안·복구/재현 예약 → 진행자 |
| 보고서 | 연구 보고·재현 연구원 | 주장이 실제 관측·비교·산출물로 뒷받침되는가? | 가설·run·실패·선택·표·그림·재현 기록 | 주장-근거 행, 원고·부록의 누락·과장 검토 → 원고 |

**페어리뷰 연구원**은 도메인을 가로지르는 별도 관점이다. 작성자가 정리한 버전과 증거를 받아 반례·계약 위반·핵심 누락을 검토한다. 계획을 대신 작성한 뒤 같은 결과를 독립 검토했다고 처리하지 않는다.

**진행자/결정 책임자**는 근거와 예산에 따라 자문을 처분하고 다음 행동을 정한다. 다수결이나 전문가 전원 합의를 요구하지 않는다. 위 역할은 책임의 구분이며 매번 모든 역할을 별도 호출한다는 뜻이 아니다.

## 모델 배정의 범위

완성될 대회 연구 하네스의 역할별 모델·effort는 아직 정하지 않았다. 이후 실제 운영 구성을 할 때 별도로 결정한다. 이 저장소를 설계·구축하는 현재 작업의 에이전트 배분과 대회 연구 운영 역할의 모델 배분은 서로 다르다. 현재 구축 작업의 배분을 이 하네스의 기본 모델 설정으로 옮기지 않는다.

## 3. 실제 조언을 받는 흐름

1. 진행자가 실제 질문과 자료를 읽고 주 도메인을 선택한다. 파일명·단어 규칙이 연구 대상을 대신 결정하지 않는다.
2. 작업 ID, 질문, 검토 범위, 근거, 대상 버전, 기대 출력, 호출 범위를 고정한다.
3. 호스트에서 이용 가능한 에이전트 도구로 실제 호출한다. 사용자가 모델·effort를 지정했다면 그대로 요청한다.
4. 응답의 실제 범위·한계·쟁점을 기록한다. 요청·실제 응답·결정은 별도 기록이다.
5. 중대한 결정이면 별도 호출의 페어리뷰를 붙인다. 같은 작성자가 이름만 바꾸는 것은 독립성이 아니다.
6. 진행자가 각 쟁점을 수정·보류·기각·위험 인수 중 하나로 처분하고 이유·근거·다음 행동을 남긴다.

에이전트 도구가 없으면 요청을 `unavailable`로 남긴다. 역할 지시문이나 자문용 자료 묶음을 만든 것만으로 `reviewed`라고 표시하지 않는다. 실제 모델/effort 영수증을 호스트가 주지 않으면 요청값만 남기고 관측값은 null이다. 다른 모델 사용만으로 검토 품질이 보장된다고 보지 않는다.

## 4. 언제 누구를 부르는가

| 변화·문제 | 기본 자문 | 페어리뷰 범위 |
|---|---|---|
| 최초 문제·가설·EDA 계획 | 연구 + 필요한 데이터 관점 | 관측/가정과 반증 가능성 |
| 분할·그룹·fitting 범위 확정/변경 | 데이터 또는 평가 | 독립성·라벨·누수·평가 의미 |
| 첫 모델·새 backbone·새 전처리 | 모델링 + 필요한 평가 관점 | 규정·입력 보존·비교 공정성 |
| P000 실측 후·긴 실행 전·GPU 변경 | 운영 | 예산·체크포인트·복구 확인 |
| 모델/ensemble 최종 선택 | 평가 | 선택 편향·추론 recipe·정확한 버전 |
| 보고서의 핵심 주장·최종 재현 | 보고서/재현 | 표·관측·주장·재현 범위의 일치 |

작은 코드 수정·단순 표 갱신·이미 검토된 계획의 동일 조건 반복 실행마다 전체 역할을 부르지 않는다. 기본은 한 쟁점의 **검토 1회 → 처분/수정 1회**다. 새로운 누수나 평가 의미 변경처럼 핵심 사실이 달라지면 그 변경만 새 버전으로 검토한다. 문체나 새 아이디어 때문에 끝없이 재검토하지 않는다.

## 5. 상태와 판단의 구분

작업 상태 제안:

```text
planned → in_progress → awaiting_review → reviewed → decided → completed
                  ↘ interrupted / failed / deferred
```

- 검토가 필요 없는 작업은 사유를 남기고 `in_progress → decided/completed`로 갈 수 있다. 검토를 생략한 것을 `reviewed`라고 표시하지 않는다.
- `reviewed`: 실제 응답이 기록된 해당 버전의 검토 상태다. 지적을 해결했다는 뜻은 아니다.
- `decided`: 지적 처분과 다음 행동이 정리됐다. 모든 결정이 실행 완료인 것은 아니다.
- `completed`: 그 작업의 완료 조건과 증거를 충족했다. 과학적 정답이나 숙련도를 뜻하지 않는다.
- 검토 후 수정: 새 해시를 만들고 `changed_after_review`로 연결한다. 재검토가 없으면 그 사실을 남긴다.
- 실행 완료와 영속 저장 확인, 복구 시험 통과는 별도 상태다.

검사기가 증명할 수 있는 것은 ID·스키마·해시·구간·참조 같은 기계적 조건이다. 가설의 타당성·제품 유형·관계 그룹·해석은 에이전트/연구자가 근거로 판단한다.

## 6. 무엇이 어떤 행동만 막는가

| 확인한 문제 | 그 입력으로 진행하면 안 되는 행동 | 계속할 수 있는 작업 |
|---|---|---|
| 가중치 출처/사용 조건 미확인 | 해당 가중치 학습·임베딩 추출 | CPU EDA·다른 후보 조사 |
| 확인된 종속 그룹의 split 교차 | 그 split의 본학습·성능 채택 | 그룹 조사·분할 수정 |
| 양성 방향·ID·전처리 경로 오류 | 그 평가·제출 산출물 채택 | 원인 분석·수정 |
| 영속 저장·복구 미확인 | 장시간 실행 | 짧은 저장·복구 시험 |
| 최종 버전·예측 재현 실패 | 최종 선택 완료 주장 | fallback 복구·리허설 |
| seed/fold가 제한됨 | 일반화 확정·유의성 과장 | 예산 내 비교·한계 명시 |
| 더 좋은 도구/모델 제안 | 막는 행동 없음 | 백로그 보관 |

새 사용자 승인 절차를 연구 단계마다 추가하지 않는다. 데이터 읽기·가설 수립·자문·검토는 현재 요청 범위다. 사용자가 지금은 설계만 진행한다고 했으므로 실행기 구현은 진행하지 않는다. 실제 대회 제출·GPU 결제는 기존에 정한 별도 명시 지시 대상으로 유지한다.

## 7. 가벼운 저장 구조 제안

```text
management/
  project.*             시간대·마감·현재 단계·연구자가 정한 한도
  tasks/                질문·작업·대상 버전·완료 조건·다음 행동
  requests/             전문가/페어리뷰 요청
  executions/           실제 호출·응답 위치·해시·한계
  reviews/              쟁점과 검토한 대상 버전
  decisions/            채택·보류·지적 처분·다음 행동
  time/                 사람 작업의 관측 구간
  sessions/             Colab 관측·상태 미확인 구간
  reservations/         탐색·재현·추론·복구의 남은 예약
  receipts/             파일 영속 저장·다운로드·복구 시험의 증거
```

이는 설계상의 역할이며 파일 확장자나 DB 선택은 아직 고정하지 않는다. 초기에는 검토 가능한 작은 JSON 기록과 단일 진행자 갱신으로 시작하는 안이다. 여러 작성자의 원자적 갱신·집계가 필요해지면 SQLite와 JSON export를 검토한다. 이미 있는 연구·실험 카드를 복제하지 않고 경로·ID·해시로 연결한다. 큰 원본·임베딩·예측·가중치는 기존 저장 위치에 두고 작은 식별/선택 기록은 Git 추적 위치를 확보한다.

## 8. 첫 운영 시나리오 — 실행 이력이 아닌 설계 예시

1. 진행자가 H001 질문과 관측 필요성을 적는다.
2. 데이터 자문은 클래스/해상도·여러 제품·결함 보존·유사 촬영 관계를 조사할 표본과 카탈로그를 제안한다.
3. CPU EDA 후 연구/평가 자문으로 가설·분할·첫 전처리를 정리한다.
4. 페어리뷰가 동일 버전의 누수·라벨·관측/추정 구분을 확인한다.
5. 진행자가 지적을 처분하고 첫 작은 실행 계획을 정한다.
6. P000에서 얻은 실제 시간·메모리·복구 결과를 운영 자문에 보낸다.
7. 운영자는 더 작은 후보 집합과 재현·추론 몫을 제안한다. 무료 GPU 잔량을 만들어내지 않는다.
8. 각 결과는 보고서 근거로 연결하며, 의미가 바뀌는 선택에만 다시 짧은 페어리뷰를 붙인다.

[기록 규약](harness/RECORDS.md), [시간·Colab 설계](RESEARCH-OPERATIONS.md), [가설·데이터 설계](HYPOTHESES-AND-DATA.md)를 함께 사용한다.

[우리 코드베이스와 대회 모델 수명주기](CODEBASE-AND-MODEL-MANAGEMENT.md)도 이 관리 대상에 포함한다. 모델 구조·학습 run·checkpoint·평가·최종 선택과 에이전트의 LLM 설정을 구분한다.

보고서 도메인의 작성 문맥·주장·절별 근거와 유효성은 [보고서 문맥 하네스](REPORT-CONTEXT-HARNESS.md)에서 구체화한다. 공통 요청/실행/검토/처분 기록을 재사용하며 별도 승인 조직을 만들지 않는다.
